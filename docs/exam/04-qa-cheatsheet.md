## ก. แนวคิดและสถาปัตยกรรม

**1. ระบบนี้คืออะไร ต่างจากแชทบอทที่ใช้ LLM ตอบอย่างไร**
ตอบ: เป็นระบบช่วยตรวจอาการเครื่องใช้ไฟฟ้าตามคู่มือ ผู้ใช้เลือกเครื่องและรุ่น พิมพ์อาการ ระบบค้นหาผังขั้นตอนที่เกี่ยวข้อง แล้ว **เครื่องสถานะ** พาตอบทีละสถานะจนถึงผล โดยทุกสถานะอ้างหน้าคู่มือ ต่างจากแชทบอทตรงที่ลำดับขั้นตอนมาจากข้อมูลที่ตรวจโครงสร้างแล้ว ไม่ได้มาจากการให้ LLM สร้างคำตอบสด
ที่มา: `backend/src/state-machine/state-machine.ts` (ตัวเดินเครื่องสถานะ) · `backend/src/execution/execution.service.ts` (ต่อทุกส่วนเข้าด้วยกัน)

**2. ทำไมไม่ใช้ RAG**
ตอบ: RAG ให้ LLM เขียนคำตอบจากข้อความที่ดึงมา ซึ่งผลอาจเปลี่ยนทุกครั้งและตรวจย้อนยาก งานนี้เป็นเรื่องความปลอดภัย จึงต้องการลำดับขั้นที่คงที่และตรวจสอบได้ ระบบนี้มีส่วนค้นหาคล้าย RAG แต่สิ่งที่ค้นคือ **ผังขั้นตอนที่เตรียมไว้** แล้วให้เครื่องสถานะเป็นคนพาเดิน เรียกว่า retrieval-guided troubleshooting state machine
ที่มา: `symptom-search/symptom-search.service.ts:170-202` (`search` คืนผังไม่ใช่ข้อความคำตอบ) · เอกสารเดิม `docs/exam-prep/13-committee-qa.md` ข้อ B4

**3. LLM ไม่มีอำนาจตัดสินใจจริงตรงไหนในโค้ด**
ตอบ: มี 3 จุดที่พิสูจน์ได้ — (ก) ตัวเดินเครื่องสถานะไม่ import อะไรนอกจากไฟล์ชนิดข้อมูล ไม่มีโค้ด LLM อยู่เลย (ข) LLM ถูกเรียก **หลัง** เครื่องสถานะเลือกสถานะแล้วเท่านั้น และทำได้แค่ปรับถ้อยคำของข้อความที่ตัดสินแล้ว (ค) ส่วนที่ LLM ร่างผังจาก PDF ผลทุกอย่างต้องผ่านตัวตรวจโครงสร้างอัตโนมัติและให้ผู้ดูแลตรวจกับหน้าต้นฉบับก่อนเผยแพร่
ที่มา: `state-machine/state-machine.ts:1-2` (import แค่ `./types`) · `execution/execution.service.ts:121-129` (เครื่องสถานะเดินก่อน) → `:194` (`displayTextOf` ค่อยเรียกปรับถ้อยคำ) · `authoring/drafts.service.ts:183-209` (`publish` ตรวจ error/warning) · prompt ของ LLM เขียนว่า "You only DRAFT" (`authoring/draft-llm.client.ts`)

**4. `resolveNextState` ทำงานอย่างไร**
ตอบ: เป็นฟังก์ชันที่รับสถานะปัจจุบัน + action ของผู้ใช้ แล้ว `switch` ตามชนิดสถานะ: คำถาม (`checkpoint`) ไป `on_yes` หรือ `on_no` ตามคำตอบ · คำสั่ง (`instruction`) ไป `next` โดยถ้าเป็นขั้นความปลอดภัยต้องส่ง `confirm_safety` ถ้าส่ง `continue` จะโยน error · อินพุต (`input`) ตรวจ regex ถ้าผ่านเก็บค่าแล้วไป `next` ไม่ผ่านไป `on_invalid` · สถานะสิ้นสุด (`resolution`/`escalation`) ไม่รับ action เลย ไม่มีการสุ่มและไม่มีการเรียกภายนอก ผลคงที่ทุกครั้ง

**6. cosine similarity คำนวณตรงไหน**

**7. ทำไมใช้โมเดลนี้ และทำไมเก็บเวกเตอร์ในหน่วยความจำ ไม่ใช้ฐานข้อมูลเวกเตอร์**

**8. เกณฑ์ 0.55 มาจากไหน และทำไมแสดงไม่เกิน 3 ผัง**
ตอบ: 0.55 เป็นค่าคงที่ในโค้ด เลือกจากชุดคำค้น 56 ข้อของโปรเจกต์เวอร์ชันก่อนที่เป็นคู่มือแอร์ ซึ่ง AI เป็นผู้ร่างและผมยังไม่ได้ตรวจทาน **จึงยังไม่ได้ปรับกับ 4 ประเภทเครื่องปัจจุบัน** — ผมยอมรับตรงๆ ว่านี่เป็นข้อจำกัด ส่วน 3 ผัง เป็นจำนวนที่ผู้ใช้อ่านเลือกได้โดยไม่ท่วม และผู้ใช้เป็นคนยืนยันผังเองก่อนเริ่ม
ที่มา: `symptom-search.service.ts:11-12` · `docs/exam-prep/03-retrieval-and-similarity.md:70` · `docs/exam-prep/10-evaluation.md` (ตาราง "ชุดตั้งเกณฑ์ 56 ข้อ")

ตอบ: ไม่ใช่ครับ เป็นค่า cosine ระหว่างข้อความที่พิมพ์กับข้อความอาการที่ใกล้ที่สุดของผังนั้น บอกได้แค่ว่า "ข้อความคล้ายกันแค่ไหน" ไม่ได้บอกว่าผังนั้นถูกต้อง หน้าเว็บจึงเรียกว่า "คะแนนความคล้ายกับที่พิมพ์ค้นหา" และมีข้อความกำกับว่า "ระบบเสนอให้เลือก ไม่ได้ตัดสินแทน" · คะแนน 1.000 แปลว่าข้อความตรงกับคำพ้องในข้อมูลทุกตัวอักษร ไม่ได้แปลว่าแม่นยำ 100%

**10. ถ้าผู้ใช้พิมพ์สิ่งที่ไม่มีในคู่มือ หรือพิมพ์ผิดเครื่อง ระบบทำอย่างไร**

## ค. ความปลอดภัย

**11. ด่านความปลอดภัยทำงานอย่างไร ข้ามได้ไหม**
ตอบ: ข้ามไม่ได้ครับ สถานะคำสั่งที่ถูกทำเครื่องหมาย `safety_critical` รับแค่ action `confirm_safety` ถ้าส่ง `continue` เครื่องสถานะโยน `SafetyConfirmationRequiredError` ซึ่ง backend แปลงเป็น HTTP 400 รหัส `SAFETY_CONFIRMATION_REQUIRED` ฝั่งหน้าเว็บก็ทำปุ่มยืนยันกดไม่ได้จนกว่าจะติ๊ก แต่ด่านจริงอยู่ที่ backend ผมลองรันเครื่องสถานะจริงแล้วยืนยันผลนี้
ที่มา: `state-machine/state-machine.ts:90-102` · `state-machine/types.ts:135-139` · `common/error-handler.ts:15` · `frontend/src/components/step/SafetyGateStep.tsx:30`

**12. ใครกำหนดว่าขั้นไหนเป็นขั้นความปลอดภัย และกำหนดถูกไหม**
ตอบ: ธง `safety_critical` เป็นข้อมูลของแต่ละสถานะในผัง กำหนดตอนแปลงคู่มือเป็นผัง ตัวตรวจโครงสร้างบังคับว่า ขั้นที่มีธงต้องมีข้อความคำเตือน และห้ามมีข้อความคำเตือนโดยไม่มีธง (`E_SAFETY_NO_WARNING`, `E_SAFETY_WARNING_WITHOUT_FLAG`) และจะ **เตือน** ถ้าข้อความของสถานะพูดถึงเรื่องที่อาจอันตราย (ไฟฟ้า ปลั๊ก แก๊ส ความร้อน) แต่ไม่มีธง (`W_STATE_RISK`) แต่ระบบ **ไม่รับประกัน** ว่าไม่มีขั้นอันตรายที่ตกหล่น ถ้า AI ร่างหรือคนแปลงพลาด เป็นเรื่องที่ผู้ดูแลต้องตรวจเทียบคู่มือก่อนเผยแพร่ และผมยังไม่ได้ให้คนตรวจธงความปลอดภัยทุกผังที่มีอยู่
ที่มา: `authoring/flow-validator.ts` (รหัส `E_SAFETY_*`, `W_STATE_RISK` ราวบรรทัด 379) · `scripts/seed-flows.js` (`validateManual` ตรวจซ้ำก่อนเข้าฐาน) · `flow-admin/flow-admin.service.ts:54-58` (admin แก้ข้อความคำเตือนได้เฉพาะขั้นที่เป็นขั้นความปลอดภัยอยู่แล้ว แก้ธงเองไม่ได้)

**13. ชั้นเรียบเรียงถ้อยคำของ LLM เปลี่ยนความหมายของคำเตือนได้ไหม**
ตอบ: ออกแบบให้ทำไม่ได้ใน 3 ชั้น (ก) **ไม่ปรับถ้อยคำเลย** กับขั้นความปลอดภัยและสถานะสิ้นสุด (ข) ข้อความที่ปรับต้องผ่านด่านตรวจ: ความยาว 0.5–1.6 เท่าของต้นฉบับ ตัวเลขต้องตรงทุกตัว ชื่อ/รหัสภาษาอังกฤษต้องตรง จำนวนคำว่า "ไม่" ต้องเท่าเดิม ห้ามลิงก์/markdown/หลายย่อหน้า ไม่ผ่านก็ใช้ต้นฉบับ (ค) หน้าเว็บแสดงลิงก์ให้ดูข้อความต้นฉบับจากคู่มือเสมอเมื่อมีการปรับ · แต่ด่านตรวจเป็นกฎอย่างง่าย ไม่ได้เข้าใจความหมาย จึงเป็นความเสี่ยงที่ลดได้ไม่ใช่ศูนย์ — และ production เปิดชั้นนี้อยู่หรือไม่ ผมต้องเช็กในแดชบอร์ด Render
