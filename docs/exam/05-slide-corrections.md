# 05 — รายการแก้สไลด์ 18 หน้า (พร้อมข้อความใหม่ที่แปะได้เลย)

> เขียนเมื่อ 7 พ.ย. 2569 จากผลไฟล์ 01–04 · **ผมไม่ได้เห็นสไลด์ตัวจริง** (ได้แค่ชื่อ 18 หน้าและรายการข้ออ้างที่ให้ตรวจ) จึงเขียนเป็น "ถ้าหน้านี้พูดว่า … ให้แก้เป็น …" · หน้าที่ไม่มีข้ออ้างที่ตรวจได้จากโค้ด ผมบอกไว้ว่า "ไม่ต้องแก้" ถ้าสไลด์จริงมีข้อความที่ต่างจากที่ผมเดา ให้ส่งมาเทียบ
> ข้อความใหม่ทั้งหมดใช้ศัพท์: **เครื่องสถานะ / สถานะ / การเปลี่ยนสถานะ / ผังขั้นตอน** · ไม่อ้างตัวเลขของตัวจำแนกประเภทสถานะที่ถูกตัดออก ไม่อ้างจำนวนเส้นทางจากการจำลอง และไม่เรียกคะแนนความคล้ายว่าความแม่นยำหรือความน่าจะเป็น

## หน้า 3 — scope 🔴

**ตรวจ:** ถ้ามี "แอร์ / AR70H / 13 ผัง / 95 สถานะ" → ลบ (ไม่อยู่ในระบบแล้ว ไฟล์ 01 ข้อ 10.1) · ถ้าเขียนว่า "คู่มือซ่อม" หรือ "SelfRepair" → แก้ (20 จาก 25 เล่มเป็นคู่มือผู้ใช้) · ถ้าเขียน "5 ประเภท" หรือรวมเตา → แก้ (เตา 2 เล่ม seed ไม่ได้)

**ข้อความใหม่:**
> **ขอบเขตข้อมูล:** คู่มือ Samsung 25 เล่ม ใน 4 ประเภทเครื่อง ได้แก่ ไมโครเวฟ ตู้เย็น โทรทัศน์ และเครื่องซักผ้า แปลงเป็นผังขั้นตอน 722 ผัง (6,322 สถานะ) · เป็นคู่มือผู้ใช้ 20 เล่ม และ service manual 5 เล่ม
> **ไม่อยู่ในขอบเขต:** เครื่องปรับอากาศ, เตา/เตาไฟฟ้า, ยี่ห้ออื่น, การวินิจฉัยด้วยเซนเซอร์, การรับประกันความถูกต้องของการซ่อม
> **ระบบแนะนำขั้นตอนตามคู่มือเท่านั้น ไม่ใช่การวินิจฉัยโดยผู้เชี่ยวชาญ**

## หน้า 4 — idea 🟡

**ตรวจ:** ถ้าเขียนว่า "AI วินิจฉัย", "RAG", "แชทบอท" → แก้

**ข้อความใหม่:**
> **แนวคิด:** ใช้ **เครื่องสถานะแบบกำหนดแน่นอน** ตัดสินลำดับขั้นตอน และใช้ AI เฉพาะงานที่ไม่ตัดสินใจแทน คือ (1) ค้นหาผังจากอาการที่พิมพ์ด้วยความคล้ายของข้อความ (2) ปรับถ้อยคำให้อ่านง่าย โดยแสดงข้อความต้นฉบับจากคู่มือได้เสมอ (3) ร่างผังจากคู่มือ PDF ให้ผู้ดูแลตรวจก่อนเผยแพร่
> **ไม่ใช่ RAG:** สิ่งที่ค้นคือผังขั้นตอนที่ตรวจโครงสร้างแล้ว ไม่ใช่ข้อความให้ LLM เขียนคำตอบ — เรียกว่า retrieval-guided troubleshooting state machine

## หน้า 5 — dfm 🟡

**ตรวจ:** ถ้าเขียนจำนวนเส้นทางหรือผลจำลอง → **ลบตัวเลขนั้น** (ห้ามอ้าง) · ถ้าเขียนว่า "ธงความปลอดภัยอยู่ที่สถานะคำสั่งเท่านั้น" → ธงอยู่ได้กับทุกชนิดสถานะในข้อมูล แต่ด่านบังคับยืนยันทำงานกับสถานะคำสั่ง (`state-machine.ts:90-102`) ถ้าอยากพูดให้แคบ: "ด่านบังคับกับสถานะคำสั่งที่ทำเครื่องหมายความปลอดภัย"

**ข้อความใหม่:**
> **เครื่องสถานะ 5 ชนิดสถานะ:** คำถาม (checkpoint) · คำสั่ง (instruction) · อินพุต (input) · ผลสรุป (resolution) · ส่งต่อศูนย์บริการ (escalation)
> **การเปลี่ยนสถานะ** เก็บเป็นตาราง `state_transitions` (คีย์หลัก = ผัง + สถานะต้นทาง + สัญลักษณ์ yes/no/next/invalid) จึงเป็นแบบกำหนดแน่นอน: สถานะหนึ่งมีทางไปต่อได้ทางเดียวต่อหนึ่งสัญลักษณ์ · ตารางเชื่อมด้วยคีย์นอกทั้งสองปลาย ชี้ไปสถานะที่ไม่มีไม่ได้
> สถานะสิ้นสุด (ผลสรุป/ส่งต่อ) ไม่รับ action เพิ่ม

## หน้า 6 — arch 🔴

**ตรวจ:** NestJS → Express · "เก็บเวกเตอร์ใน MySQL" → ไม่ใช่ (อยู่ในหน่วยความจำ) · Python/pandas/NumPy/pdfplumber/sentence-transformers → ไม่มีใน repo (ใช้ Node.js และ `unpdf`) · ถ้าเขียน "ไม่มีการยืนยันตัวตน" → แก้

**ข้อความใหม่:**
> **สถาปัตยกรรม:** หน้าเว็บ React + Vite + Tailwind (GitHub Pages) → backend **Express 4 + TypeScript** (Render) → MySQL เขียน SQL ตรงด้วย mysql2 ไม่ใช้ ORM
> backend มี 6 ส่วน: ตรวจอาการ (เครื่องสถานะ) · ค้นอาการ (โมเดลฝังความหมายรันในเครื่อง เวกเตอร์เก็บในหน่วยความจำ) · เรียบเรียงถ้อยคำ (Groq ไม่บังคับ) · บัญชีผู้ใช้ (JWT) · ประวัติ/คะแนน · ผู้ดูแลระบบ (ร่างผังจาก PDF, จัดการผังที่เผยแพร่, สถิติ)
> API **30 เส้นทาง** · ฐานข้อมูล **12 ตาราง** · ย้ายจาก NestJS เป็น Express เพื่อให้โค้ดอธิบายได้ทุกบรรทัด

## หน้า 7 — flow 🟡

**ตรวจ:** ลำดับในสไลด์ต้องมี "เลือกประเภทเครื่องและรุ่น" ก่อนพิมพ์อาการ (หน้าเว็บบังคับ ส่ง `manualId` เสมอ) · ถ้าเขียนว่าฟังก์ชันชื่อ `resolveNextNode` → แก้เป็น **`resolveNextState`**

**ข้อความใหม่:**
> **ลำดับการทำงาน:** เลือกประเภทเครื่อง → เลือกรุ่น → พิมพ์อาการ (ค้นเฉพาะคู่มือรุ่นนั้น) → เลือกผังจากที่ระบบเสนอ (≤ 3 ผัง) → ตอบทีละสถานะ ให้ `resolveNextState` เลือกสถานะถัดไป → ผลสรุป → บันทึกผลลัพธ์ (ไม่บังคับ) → ดูประวัติ/ให้คะแนน
> ทุกสถานะอ้างหน้าคู่มือ · session ที่ยังไม่จบกลับมาทำต่อได้ 7 วัน

## หน้า 8 — safety 🟡

**ตรวจ:** ต้องมีบรรทัดว่า 400 `SAFETY_CONFIRMATION_REQUIRED` · ถ้าเขียนว่า "AI ปรับถ้อยคำคำเตือน" → แก้ (ไม่ปรับ)

**ข้อความใหม่:**
> **ด่านความปลอดภัย (บังคับที่ backend):** สถานะคำสั่งที่ทำเครื่องหมาย `safety_critical` รับได้เฉพาะ `confirm_safety` · ส่ง `continue` → เครื่องสถานะปฏิเสธ → **HTTP 400 `SAFETY_CONFIRMATION_REQUIRED`** (หน้าเว็บทำปุ่มกดไม่ได้อีกชั้น แต่ด่านจริงอยู่ที่ backend)
> **ข้อความที่เป็นคำเตือนและสถานะสิ้นสุดไม่ถูกปรับถ้อยคำด้วย AI** · ข้อความที่ปรับต้องผ่านด่านตรวจ (ความยาว ตัวเลข ชื่อ/รหัส จำนวนคำว่า "ไม่") ไม่ผ่านใช้ต้นฉบับ
> **ข้อจำกัด:** ด่านนี้ทำงานกับขั้นที่ผังทำเครื่องหมายไว้ ความครบถ้วนของการทำเครื่องหมายขึ้นกับข้อมูลที่แปลงจากคู่มือ

## หน้า 9 — match 🔴

**ตรวจ:** โมเดล · ค่าเกณฑ์ · จำนวนสูงสุด · "ความแม่นยำ/ความน่าจะเป็น" → ลบ · "เก็บใน MySQL" → แก้ · ที่มา 0.55

**ข้อความใหม่:**
> **ค้นอาการ:** โมเดลฝังความหมาย `paraphrase-multilingual-MiniLM-L12-v2` (ควอนไทซ์ 8 บิต · 384 มิติ · รันในเครื่อง ไม่ฝึกเอง) · ตอนเซิร์ฟเวอร์เริ่ม ฝังข้อความอาการของทุกผัง (ชื่อไทย ชื่ออังกฤษ คำพ้อง) เก็บ **ในหน่วยความจำ** (production: 4,129 ข้อความ จาก 670 ผัง)
> ผู้ใช้พิมพ์ → ฝังข้อความ → เทียบ **cosine similarity** → เสนอผังที่ **คะแนนความคล้าย ≥ 0.55 ไม่เกิน 3 ผัง** ในคู่มือที่เลือก
> **คะแนนคือความคล้ายของข้อความ ไม่ใช่ความแม่นยำหรือความน่าจะเป็น** · ผู้ใช้เป็นคนเลือกผัง
> **ข้อจำกัด:** เกณฑ์ 0.55 เลือกจากชุดคำค้นของคู่มือแอร์ในเฟสแรก ยังไม่ได้ปรับกับ 4 ประเภทเครื่องปัจจุบัน และ **ไม่ใช่ขอบเขตความปลอดภัย** (ตัวอย่างพิมพ์เรื่องทีวีในคู่มือเครื่องซักผ้ายังได้ผังที่ผ่านเกณฑ์) · ตัวค้นหาจับรหัสข้อผิดพลาดได้ไม่ดี

## หน้า 10 — convert 🔴

**ตรวจ:** ตัวเลข "631 ผัง / 4,739 สถานะ / 644 ผัง / 22 คู่มือ" เป็นของเก่า → แก้ · "ตรวจสอบแล้ว" → ระบุว่าตรวจอะไร · AR70H → ลบ

**ข้อความใหม่:**
> **จากคู่มือถึงผังขั้นตอน:** PDF → ข้อความรายหน้า → ผังขั้นตอน (ไฟล์ JSON) → **ตัวตรวจโครงสร้างอัตโนมัติ** → ฐานข้อมูล (ตาราง `flows`, `states`, `state_transitions`)
> **ตัวเลขข้อมูลที่ใช้ seed ได้:** 25 คู่มือ · 722 ผัง · 6,322 สถานะ (production ขณะนี้ 670 ผัง)
> **ตรวจแล้ว:** ทุกการเปลี่ยนสถานะชี้ไปสถานะที่มีจริง · ขั้นความปลอดภัยมีข้อความคำเตือน · ข้อความหน้าอ้างอิงอยู่ในช่วงที่ถูกต้อง · **ยังไม่ได้ตรวจโดยคน:** คำแปลภาษาไทยและความถูกต้องของลำดับขั้น
> **เส้นทางใหม่:** ผู้ดูแลอัปโหลด PDF ให้ AI ร่าง → ตัวตรวจโครงสร้าง → ผู้ดูแลตรวจเทียบหน้าต้นฉบับ → เผยแพร่ (ผังที่ AI ร่างยังไม่เคยทดสอบกับ Groq จริงหลังย้ายเป็น Express — ถ้าจะเดโมให้ทดลองก่อน)

## หน้า 11 — roles 🔴

**ตรวจ:** "guest / user / admin" → แก้ · "ไม่มีการยืนยันตัวตน" → แก้ · admin "เพิ่ม ดู แก้ไข ลบ" ต้องระบุข้อจำกัด

**ข้อความใหม่:**
> **บทบาท 2 แบบ:** ผู้ใช้ (`user`) และผู้ดูแลระบบ (`admin`) · สมัครผ่านหน้าเว็บได้เฉพาะ `user` · `admin` สร้างได้ทางเดียวคือสคริปต์ของผู้พัฒนา · **ผู้ใช้ที่ไม่ล็อกอิน** ตรวจอาการได้และมีประวัติผูกกับรหัสในเบราว์เซอร์ (ไม่ใช่การยืนยันตัวตน)
> **ล็อกอิน:** รหัสผ่านแฮชด้วย bcrypt · JWT (HS256) อายุเริ่มต้น 7 วัน · ระบบตรวจบทบาทจากฐานข้อมูลทุกครั้งที่เข้าหน้า admin
> **ผู้ดูแลระบบทำได้:** ดูสถิติและความเห็นผู้ใช้ · **เพิ่ม**คู่มือใหม่ผ่าน PDF → AI ร่าง → ตรวจ → เผยแพร่ · **ดู**ผังที่เผยแพร่ · **แก้เฉพาะข้อความ**ของสถานะ (แก้โครงสร้างไม่ได้ มีประวัติการแก้) · **ลบ**แบบซ่อนและกู้คืนได้

## หน้า 15 — limits 🔴

**ข้อความใหม่:**
> **ข้อจำกัดที่ทราบ:**
> 1. เกณฑ์ค้นหา 0.55 ไม่ใช่ขอบเขตความปลอดภัย และยังไม่ได้ปรับกับข้อมูลปัจจุบัน
> 2. ข้อมูลที่ตรวจแล้วมีจำกัด: ตรวจโครงสร้างอัตโนมัติ ยังไม่ได้ให้คนตรวจคำแปลและลำดับขั้น · เป็นคู่มือผู้ใช้เสียส่วนใหญ่ · ครอบคลุม 4 ประเภทของยี่ห้อเดียว
> 3. ใช้โมเดลสำเร็จรูป ไม่ได้ฝึกโมเดลเอง
> 4. ผลลัพธ์และคะแนนที่ผู้ใช้กรอกไม่ได้ทำให้ระบบเรียนรู้ — เก็บไว้ให้ผู้ดูแลอ่านและปรับปรุงผังด้วยมือ
> 5. ยังไม่ได้ทดสอบกับผู้ใช้จริง และไม่มีเทสต์อัตโนมัติ
> 6. ด้านการใช้งาน: เซิร์ฟเวอร์ตัวเดียว · ไม่มี rate limit ที่หน้าล็อกอิน · เซิร์ฟเวอร์ฟรีต้องรอเริ่มทำงานราว 2–3 นาทีก่อนค้นอาการได้
