## ส่วน A: คำถามจากหัวข้อ 7 ของ handoff (ตอบได้หลังอ่านถึงขั้น 6.3)

### A1. ตัวตนของผู้ใช้ฝั่งหน้าจอมี 3 ชั้นอะไร
- ชั้น 1: สถานะใน `AuthContext` (`status`, `user`) ที่ `AuthProvider` ถือ (`AuthProvider.tsx:105-110`)
- ชั้น 2: `useIdentity()` ใช้ id ผู้ใช้ (หรือ `'guest'`) เป็นส่วนของ `queryKey` ในแคช (`authContext.ts:28-30`, `queries.ts`)
- ชั้น 3: `ownerHeaders()` แนบ `X-Client-Id` เมื่อไม่มี token เพื่อให้ backend รู้เจ้าของเซสชันของ guest (`clientHeaders.ts:4-6`)

### A2. ทำไมต้อง `queryClient.clear()` ตอนล็อกอิน/ออกจากระบบ
- เพื่อให้ผู้ใช้คนก่อนไม่เหลือข้อมูลในหน่วยความจำ (คอมเมนต์ `AuthProvider.tsx:20-21`) เป็นชั้นป้องกันซ้อนกับ `identity` ในป้ายแคช
- อยู่ที่ `applySession` (:78), `logout` (:101), ตัวรับสัญญาณ 401 (:46)

### A3. `request()` ใน `http.ts` ทำอะไรบ้างตามลำดับ และทำไม 401 ของการล็อกอินไม่เด้งไปหน้าล็อกอินซ้ำ
- ลำดับ: ต่อ URL → หา token (ข้ามถ้า `anonymous`) → ประกอบหัวข้อความ → `fetch` (ล้มเหลวแปลงเป็น `NETWORK_ERROR` รหัส 0) → ถ้าไม่ `ok` อ่าน error, ถ้า 401 และเคยแนบ token ก็เรียกตัวรับสัญญาณ แล้ว `throw ApiError` → ถ้า 204 คืน `undefined` → ไม่งั้นคืนผล JSON (`http.ts:39-86`)
- 401 ตอนล็อกอินไม่เด้งซ้ำ เพราะ `login` ใส่ `anonymous: true` (`auth.ts:21`) ทำให้ `token` เป็น `undefined` เงื่อนไข `http.ts:70` (`token !== undefined`) เป็นเท็จ

### A4. หน้าเดินผังเอาข้อมูลจากไหน (แคชของ React Query vs ยิงไป server) ⭐ ช่วง 5
- เส้นทางปกติ: `startSession` ยิง `POST /traversal/sessions` → ได้ `SessionResponse` → `useCacheSession` เขียนลงแคชป้าย `['session', identity, id]` → พาไป `/session/:id` → `useSession(id)` อ่านป้ายเดียวกัน จึงเห็นข้อมูลทันที (`queries.ts:103-137`)
- ทุกครั้งที่กดตอบ: `useSubmitAction` ยิง `POST .../actions` → server ตอบสถานะใหม่ → เขียนทับในแคช
- ถ้าแคชว่าง (เช่น รีเฟรชหน้า): `useSession` ยิง `GET /traversal/sessions/:id` เอง (`traversal.ts:50-52`)
- ข้อสันนิษฐานยังไม่ทดสอบ: `App.tsx:21-28` ไม่ตั้ง `staleTime` ค่าเริ่มต้นคือ 0 หน้า `SessionPage` อาจแสดงจากแคชก่อนแล้วยิง `GET` ซ้ำเบื้องหลัง ต้องเช็กตอนอ่าน `SessionPage` หรือดู Network tab
- หน้าจอรู้ว่า "อยู่ขั้นไหน" จากช่อง `node` (ชนิด `RenderedNode`) ใน `SessionResponse` (`types.ts:41-50`) ไม่ต้องคำนวณเอง

### A5. `AdminRoute` กับ `requireAdmin` ต่างกันยังไง ใครเป็นตัวบังคับจริง
- `AdminRoute` เป็น UX ฝั่งหน้าจอ (คอมเมนต์ `AdminRoute.tsx:16-17`): ใครแก้ localStorage ให้ role เป็น admin ก็เห็นหน้าได้
- `requireAdmin` ฝั่ง backend ตรวจ token จริงและตอบ 401/403 คือตัวบังคับจริง
- ยังไม่ได้เปิดไฟล์ backend รอบ frontend นี้ ข้อนี้อ้างจากคอมเมนต์ในโค้ดและ `READING-PROGRESS.md`

## ส่วน B: คำถามรายไฟล์

### `main.tsx` (ขั้น 6.1)

- B2. `main.tsx` จำเป็นต้องรู้จักหน้า Login หรือ History ไหม
  - เฉลย: ไม่ต้อง รู้จักแค่ `App` ตัวเดียว เรื่องหน้าไหนอยู่ path ไหนเป็นงานของ `App.tsx`

### `App.tsx` (ขั้น 6.1)
- B3. ถ้าย้าย `queryClient = new QueryClient(...)` เข้าไปในฟังก์ชัน `App` จะเกิดอะไร
  - เฉลย: ทุกครั้งที่ `App` วาดใหม่ได้ตู้แคชใบใหม่ ข้อมูลที่เคยดึงหายหมด ต้องดึงใหม่ จึงต้องวางไว้นอกฟังก์ชัน (`App.tsx:21`)
- B4. ถ้าเอา `AuthProvider` ไปไว้นอก `QueryClientProvider` จะพังตรงไหน
  - เฉลย: `AuthProvider` เรียก `useQueryClient()` เพื่อล้างแคช (`AuthProvider.tsx:27`) แต่ตอนนั้นยังไม่มี provider ครอบ จะ error ว่าหา `QueryClient` ไม่เจอ
- B5. เปิดเว็บที่ `/admin` ผู้ใช้ทั่วไปไปจบที่ไหน
  - เฉลย: `/admin` เด้งไป `/admin/analytics` (`App.tsx:50`) แล้ว `AdminRoute` ตัดสิน: guest → หน้าล็อกอิน (พร้อมจำหน้านี้), ล็อกอินแต่ไม่ใช่ admin → `ForbiddenPage` (`AdminRoute.tsx:32-38`)

### `AppShell.tsx` (ขั้น 6.1)
- B6. ถ้าเอา `end` ออกจากเมนู "หน้าแรก" จะเกิดอะไร
  - เฉลย: ทุกหน้าขึ้นต้นด้วย `/` ดังนั้น "หน้าแรก" จะถูกไฮไลต์ตลอด และเมนูของหน้าปัจจุบันก็ไฮไลต์คู่กัน 2 อัน (`AppShell.tsx:40`)
- B7. เปิด `/history/abc` เมนูไหนสว่าง ทำไม
  - เฉลย: "ประวัติการซ่อม" เพราะ `/history/abc` ขึ้นต้นด้วย `/history` และเมนูนี้ไม่มี `end` ส่วน "หน้าแรก" ไม่สว่างเพราะมี `end`
- B8. ผู้ใช้ทั่วไปแก้ role เป็น admin ในเบราว์เซอร์ จะเห็นเมนูผู้ดูแลระบบ แล้วเข้าได้จริงไหม
  - เฉลย: เห็นเมนู (`AppShell.tsx:28`) แต่ข้อมูลจริงเข้าไม่ได้ เพราะ API ฝั่ง backend ตรวจ role จาก token ที่เซิร์ฟเวอร์เซ็น
- B9. ทำไมต้องส่ง `children` เข้า `AppShell`
  - เฉลย: เพื่อให้กรอบเป็นของกลาง หน้าไหนก็ถูกแทรกลงตรง `{children}` (`AppShell.tsx:76`) โดยกรอบไม่ต้องรู้ว่ามีกี่หน้า

### `http.ts` + `authStorage.ts` (ขั้น 6.2)
- B10. ทำไมต้องมีเงื่อนไข `token !== undefined` ก่อนเรียกตัวรับสัญญาณ 401
  - เฉลย: เพื่อแยก "token หมดอายุ" (ต้องล็อกเอาต์) ออกจาก "ไม่เคยมี token" เช่น รหัสผ่านผิดตอนล็อกอิน ถ้าไม่แยกจะเด้งวนไปหน้าล็อกอินทั้งที่ผู้ใช้แค่พิมพ์รหัสผิด (`http.ts:70`)
- B11. ถ้า `localStorage` ใช้ไม่ได้ ผู้ใช้ล็อกอินได้ไหม
  - เฉลย: ได้ในแท็บนั้น เพราะ `storeAuth` ตั้ง `memory` ก่อน แล้วเงียบเมื่อเขียน `localStorage` ล้มเหลว (`authStorage.ts:50-56`) แต่ปิดแท็บหรือรีเฟรชแล้วต้องล็อกอินใหม่
- B12. ทำไม `anonymous` ต้องมีทั้งที่แค่ไม่ส่ง `headers` ก็ได้
  - เฉลย: เพราะ token ถูกแนบอัตโนมัติจาก `authStorage` ภายใน `request()` ผู้เรียกไม่ได้ส่ง `Authorization` เอง ถ้าอยากยิงโดยไม่แนบต้องมีสวิตช์นี้ (`http.ts:43`)

### `auth.ts` (ขั้น 6.2)
- B13. ทำไม `login` ต้องใส่ `anonymous: true` ทั้งที่ยังไม่ล็อกอินอยู่แล้ว
  - เฉลย: อาจมี token เก่าค้างใน `localStorage` ถ้าแนบไปแล้วได้ 401 จะเข้าเงื่อนไข `http.ts:70` ทำให้แอปเด้งไปหน้าล็อกอินซ้ำ `anonymous` ตัดทางนี้ทิ้ง
- B14. ถ้า backend ตอบ `email` มาด้วย อีเมลจะไปอยู่ที่ไหนในแอป
  - เฉลย: ไม่อยู่ที่ไหน `toAuthUser` หยิบแค่ `id`, `displayName`, `role` (`auth.ts:9-11`)
- B15. `getMe` ต่างจาก `login` ตรงไหน
  - เฉลย: `getMe` แนบ token (ไม่มี `anonymous`) เป็น GET ใช้ยืนยัน token เดิม ส่วน `login` ไม่แนบ token เป็น POST ใช้แลก email+password เป็น token ใหม่
- B16. ทำไมต้องแปลง `accessToken` เป็น `token`
  - เฉลย: ให้ชื่อฟิลด์ตรงกับ `StoredAuth` ที่เก็บใน `authStorage.ts` ใช้รูปเดียวกันทั้งแอป (`auth.ts:13-15`)

### `queries.ts` (ขั้น 6.2) ⭐
- B17. ทำไม identity ต้องอยู่ในป้ายแคช
  - เฉลย: ไม่ให้ข้อมูลของคนหนึ่งไปโผล่ให้อีกคนเห็นเมื่อสลับบัญชีในเบราว์เซอร์เดียวกัน คู่กับ `queryClient.clear()`
- B18. ทำไมค้นอาการใช้ `useMutation` ไม่ใช่ `useQuery`
  - เฉลย: ค้นเฉพาะตอนกดปุ่ม และผลขึ้นกับสถานะ server (โมเดลอาจยังโหลดไม่เสร็จ ตอบ `SEARCH_NOT_READY`) จึงไม่ควรเก็บผลเก่าในแคช (คอมเมนต์ `queries.ts:90-96`)
- B19. `setQueryData` ต่างจาก `invalidateQueries` อย่างไร
  - เฉลย: `setQueryData` ใส่ค่าใหม่ลงแคชทันทีโดยไม่ถาม server ใช้เมื่อมีคำตอบล่าสุดในมือ ส่วน `invalidateQueries` บอกว่า "ของเก่า" แล้วให้ไปดึงใหม่ ใช้เมื่อไม่รู้ว่า server เปลี่ยนอะไร
- B20. `staleTime: Infinity` ของ `useGraphs` กับการ `invalidate ['graphs']` ใน `usePublishDraft` ขัดกันไหม
  - เฉลย: ไม่ขัด `Infinity` แค่บอกว่าไม่ต้องดึงใหม่เอง ส่วน `invalidateQueries` บังคับให้ดึงใหม่ได้ ใช้คู่กัน: ปกติไม่ดึง ยกเว้นตอนมีผังใหม่ถูกเผยแพร่ (`queries.ts:45,245`)
- B21. ทำไมลบประวัติใช้ `onSettled` สำหรับ invalidate แต่ลบแคชเดี่ยวใช้ `onSuccess`
  - เฉลย: ทิ้งแคชรายละเอียดควรทำเมื่อลบสำเร็จเท่านั้น แต่รายการรวมควรดึงใหม่ไม่ว่าผลเป็นอย่างไร (อนุมานจากโครงโค้ด ผู้เขียนไม่ได้เขียนเหตุผลไว้) (`queries.ts:150-163`)

- D79. ช่อง "ถึงวันที่" รวมวันที่เลือกไว้ด้วยไหม และตีความเป็นเขตเวลาไหน

- D80. หน้าจอป้องกันช่วงวันที่ผิดไหม
  - เฉลย: บางส่วน ช่อง "ตั้งแต่" มี `max={params.to}` และช่อง "ถึง" มี `min={params.from}` กันเลือกกลับด้าน (`AdminFeedbackPage.tsx:67,79`) แต่ผู้ใช้พิมพ์ผ่าน URL ได้ ฝั่ง backend จึงตรวจซ้ำว่า `from` ไม่หลัง `to` และช่วงไม่เกิน 366 วัน (`admin.dto.ts:77-84`, ค่าคงที่ `:10`) หน้าจอไม่ได้จำกัด 366 วัน ถ้าเลือกเกิน backend ตอบ error และหน้าแสดง `ErrorNotice` (ยังไม่ได้ทดสอบ)
- D81. แถวความเห็นแสดงข้อมูลระบุตัวผู้ให้ความเห็นไหม
  - เฉลย: ไม่ แสดงเพียงคะแนน เวลา ชนิดเจ้าของ (ผู้ใช้/ผู้เยี่ยมชม/ไม่ระบุ) ข้อความ ประเภทเครื่อง และยี่ห้อ (`AdminFeedbackPage.tsx:129-158`) ชนิดข้อมูล `AdminFeedbackItem` ไม่มีช่องอีเมลหรือรหัสผู้ใช้ (`types.ts:121-131`) และ `sessionId` ใช้เป็น `key` เท่านั้น ไม่ได้ทำลิงก์ไปดูเซสชัน
- D82. ข้อความความเห็นของผู้ใช้แสดงอย่างไร ปลอดภัยไหม
  - เฉลย: แสดงเป็นข้อความธรรมดาใน `<p className="whitespace-pre-wrap break-words">` React ไม่ตีความเป็น HTML คงการขึ้นบรรทัดใหม่ ถ้าไม่มีข้อความแสดง "(ไม่มีข้อความ)" (`AdminFeedbackPage.tsx:146-150`) ข้อสรุปเรื่อง React เป็นความรู้ทั่วไป ไม่ได้ทดสอบกับข้อความที่มีแท็ก

### `lib/errors.ts` + `components/ErrorNotice.tsx` (ขั้น 6.7 ใช้ทั่วทั้งแอป)
- D84. ทำไม `describeError` ตัดสินจาก `code` ไม่ใช้ `message` ที่เซิร์ฟเวอร์ส่งมา
  - เฉลย: ข้อความของ backend เขียนให้นักพัฒนาอ่าน มีรหัสสถานะภาษาอังกฤษปนอยู่ ผู้ใช้ทั่วไปอ่านไม่เข้าใจ (คอมเมนต์ `errors.ts:6-11`) ตารางข้อความไทยจึงอยู่ฝั่งหน้าจอ ยกเว้น 3 รหัสของร่างแผนผังที่ใช้ข้อความจากเซิร์ฟเวอร์ประกอบ เพราะบอกจุดผิดเจาะจงให้ผู้ดูแล: `INVALID_DRAFT_REQUEST`, `PDF_PAGE_TOO_LONG` (แทนข้อความเดิม) และ `DRAFT_ID_CONFLICT` (ต่อหน้าข้อความเดิม) (`errors.ts:263-270`)
- D85. ข้อผิดพลาดที่ไม่ใช่ `ApiError` (เช่น `TypeError`, `SyntaxError` จากการอ่าน JSON) แสดงว่าอะไร
  - เฉลย: ตกเป็น `UNKNOWN_ERROR` "เกิดข้อผิดพลาดที่ระบบไม่รู้จัก ลองอีกครั้ง..." และ recovery เป็น `retry` (`errors.ts:35-39,246-248`) ตรงกับข้อสังเกตเรื่อง `response.json()` ใน `http.ts:85` ที่อาจโยน `SyntaxError`
- D86. รหัส `UNKNOWN_ERROR` ที่สถานะ 400 มาจากไหน และต่างจากรหัสแปลกอื่นอย่างไร
  - เฉลย: `http.ts:76` ตั้งรหัส `UNKNOWN_ERROR` เมื่อเนื้อ error ของ server ไม่มี `code` ถ้าสถานะเป็น 400 `describeError` แปลเป็น "เซิร์ฟเวอร์อ่านคำขอไม่ได้" (เช่นคำขอผิดรูปแบบก่อนถึงตัวตรวจ) ส่วนรหัสอื่นที่ไม่มีในตารางได้ข้อความ "ไม่รู้จัก" (`errors.ts:250-260`)
- D87. ทำไมใช้ `Object.hasOwn(MESSAGES, error.code)` ไม่ใช้ `MESSAGES[error.code]` ตรงๆ
  - เฉลย: กันรหัสที่ชื่อซ้ำกับสมบัติในตัวของอ็อบเจ็กต์ เช่น `constructor` หรือ `toString` ซึ่งถ้าอ่านตรงๆ จะได้ฟังก์ชันของ prototype แทนที่จะเป็น `undefined` (`errors.ts:258`) เป็นความรู้ทั่วไปของ JavaScript ไม่ได้ทดสอบ
- D88. `recovery` มี 6 แบบอะไรบ้าง และ `ErrorNotice` ทำอะไรกับแต่ละแบบ
  - เฉลย: `retry` = ปุ่ม "ลองอีกครั้ง" (ถ้าส่ง `onRetry`), `reload-session` = ปุ่มที่ใช้ป้าย `reloadLabel` (ถ้าส่ง `onRetry`), `back-to-history` = ลิงก์ `/history`, `login` = ลิงก์ `/login`, `back-to-symptoms` = ลิงก์ `/symptoms/all`, `stay` = ไม่มีปุ่ม (`ErrorNotice.tsx:34-58`, ชนิดที่ `errors.ts:25`) กล่องห่อด้วย `role="alert"` ให้โปรแกรมอ่านหน้าจอประกาศทันที
- D89. `INVALID_ACTION` แปลว่าอะไรต่อผู้ใช้ และแก้อย่างไร
  - เฉลย: "หน้าจอไม่ตรงกับเซิร์ฟเวอร์" ขั้นบนหน้าจอเก่ากว่าที่ server บันทึก เช่นกดซ้ำหรือเปิดหลายแท็บ recovery เป็น `reload-session` ปุ่มแสดงป้าย "ดึงขั้นตอนล่าสุด" (`SessionPage.tsx:117,158`) ซึ่งเรียก `handleRefresh` ดึงสถานะจริงจาก server มาแทน (ต่อจาก D25)
- D90. ทำไม `SAFETY_CONFIRMATION_REQUIRED` มี recovery เป็น `stay`
  - เฉลย: ผู้ใช้ต้องกลับไปติ๊กยืนยันที่ขั้นเดิม ไม่ต้องดึงข้อมูลใหม่ ข้อความ "เซิร์ฟเวอร์ไม่ให้ข้ามขั้นตอนนี้ อ่านคำเตือนและติ๊กยืนยันก่อน" (`errors.ts:50-54`) เป็นเครื่องยืนยันว่า backend เป็นผู้บังคับด่านจริง (ต่อจาก D26)
- D91. รหัส error ของ backend ครบทุกตัวถูกแปลในตารางหรือไม่
  - เฉลย: ผมค้นสตริงรหัสที่มีเครื่องหมาย `_` ใน `backend/src/**/*.ts` เทียบกับคีย์ใน `MESSAGES` พบว่ารหัสที่เป็นรหัส API ถูกแปลครบ ยกเว้น `INTERNAL_ERROR` (ตกเป็น `UNKNOWN_ERROR` ซึ่งเหมาะกับ 500) และ `LLM_BAD_RESPONSE`, `LLM_HTTP`, `LLM_NOT_CONFIGURED`, `LLM_PARSE_ERROR`, `LLM_TIMEOUT` ซึ่งน่าจะเป็นรหัสที่บันทึกในช่อง `error` ของร่าง ไม่ผ่าน `describeError` (ยังไม่ยืนยัน ตรวจตอนอ่านกลุ่ม drafts) รหัสไม่มี `_` เช่น `UNAUTHENTICATED`, `FORBIDDEN` ค้นด้วยวิธีนี้ไม่ได้ ไม่ได้เทียบ
- D92. ทำไมบางข้อผิดพลาดแสดง "รหัส: ..." ให้ผู้ใช้เห็น
  - เฉลย: เฉพาะกรณีข้อมูลขั้นตอนไม่สมบูรณ์ (`GRAPH_NODE_MISSING`) และเผยแพร่ลงฐานข้อมูลแล้วแต่โหลดไม่สำเร็จ (`PUBLISH_RELOAD_FAILED`) เพื่อให้แจ้งผู้ดูแลระบบได้ (`errors.ts:31-32,84,240`, `ErrorNotice.tsx:32`)

  - เฉลย: เทียบกับ backend `auth.dto.ts` แล้วตรงกันทุกค่า: รหัสผ่าน 8/72 ตัวอักษร และ 72 ไบต์, อีเมลไม่เกิน 255, ชื่อ 1–100, รูปแบบอีเมล (regex) เหมือนกันทุกตัวอักษร (`authForm.ts:1-8` กับ `auth.dto.ts:5-12`) เขียนซ้ำสองที่ด้วยมือ ต้องแก้ทั้งคู่ ส่วนตอนล็อกอิน backend ตรวจอีเมลแค่ไม่ว่าง/ไม่เกิน 255 และรหัสผ่านไม่ว่าง/ไม่เกิน 1000 (`auth.dto.ts:103-108`) ฝั่งหน้าจอตรวจรูปแบบอีเมลเพิ่ม (เข้มกว่า) และไม่ตรวจเพดาน 1000

- D128. `DraftJsonEditor` ตรวจอะไรเองก่อนส่ง และส่วนที่เหลือใครตรวจ
  - เฉลย: ตรวจเฉพาะว่า `JSON.parse` ได้และผลเป็นอาร์เรย์ (`DraftJsonEditor.tsx:29-44`) จากนั้นส่ง `PUT /admin/drafts/:id` ให้ backend ตรวจรูปแบบและรัน validator ใหม่ทั้งหมด (`drafts.ts:31-34`) ฟิลด์ที่ระบบกำหนดเอง (เช่น `manual_id`, `source`) ใส่ไม่ได้ backend ปฏิเสธ (ข้อความอธิบายบรรทัด 52) ชนิด `DraftGraph[]` ที่ cast ไม่ได้ถูกตรวจฝั่งหน้าจอ
- D129. ทำไมตัวแก้ JSON ถูกใส่ `key={draft.updatedAt}`
  - เฉลย: เมื่อบันทึกและตรวจใหม่สำเร็จ `updatedAt` เปลี่ยน ทำให้ช่องแก้ถูกสร้างใหม่ด้วยข้อมูลล่าสุดจาก server (คอมเมนต์ `DraftJsonEditor.tsx:19`, ใช้ที่ `AdminDraftReviewPage.tsx:107`)
- D130. ปุ่ม "เผยแพร่ให้ผู้ใช้เห็น" เปิดเมื่อไร และใครบังคับจริง
  - เฉลย: `publishGate` เปิดเมื่อสถานะ `ready` มีรายงานการตรวจ ไม่มีข้อผิดพลาดเลย ติ๊ก "ตรวจแล้ว" และถ้ามีคำเตือนต้องติ๊กรับทราบ ไม่งั้นแสดงเหตุผลใต้ปุ่ม (`draftView.ts:148-161`) เป็น UX เท่านั้น backend ตรวจซ้ำทุกครั้ง ข้อผิดพลาด = ปฏิเสธ ไม่มีทางข้าม (คอมเมนต์ `DraftActions.tsx:14-15`, `errors.ts:221-230`)
- D131. `acknowledgedWarnings` ที่ส่งไปมีค่าอะไร
  - เฉลย: เป็นจริงเมื่อมีคำเตือนและผู้ตรวจติ๊กรับทราบเท่านั้น (`ack = warnings > 0 && warningsAcknowledged`) ถ้าไม่มีคำเตือนส่ง `false` (`draftView.ts:151,160`)
- D132. เผยแพร่ล้มเหลวแล้วหน้าทำอะไร
  - เฉลย: เรียก `onRefresh` ดึงร่างล่าสุดมาแสดงสถานะจริง (เช่นร่างถูกเผยแพร่ไปแล้ว) และแสดง `ErrorNotice` (`DraftActions.tsx:76,80`) ทั้งสำเร็จและล้มเหลว `usePublishDraft` ทำเครื่องหมายรายการร่างเก่าให้ดึงใหม่ (`queries.ts:241-243`)
- D133. เผยแพร่สำเร็จแล้วแสดงอะไร และผู้ใช้ทั่วไปเห็นของใหม่อย่างไร
  - เฉลย: แสดงจำนวนและรหัสแผนผังขั้นตอนใหม่ ว่า "ใช้งานได้ทันทีโดยไม่ต้องรีสตาร์ต" และเพิ่มเข้าระบบค้นหาด้วยข้อความหรือไม่ (`searchIndex.indexed`, ไม่ได้เพิ่มก็บอกเหตุผล และจะค้นเจอหลังรีสตาร์ต) (`DraftActions.tsx:31-50`) ฝั่งผู้ใช้ `usePublishDraft` ทำเครื่องหมายแคช `['graphs']` และ `['manuals']` ว่าเก่า (`queries.ts:244-247`) รายการรุ่นและอาการใหม่จึงปรากฏ (ต่อจาก D107)
- D134. ปฏิเสธร่างทำอย่างไร
  - เฉลย: ปฏิเสธได้เมื่อร่าง `ready` หรือ `failed` ต้องกดสองขั้น (ปฏิเสธ → ยืนยัน) เหตุผลไม่บังคับ ไม่เกิน 300 ตัวอักษร ถ้าว่างส่ง `{}` (`DraftActions.tsx:84-114`, `drafts.ts:36-40`) หลังสำเร็จแคชรายละเอียดถูกอัปเดตเป็น `rejected`
