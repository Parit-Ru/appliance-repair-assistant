## 1. จุดเริ่มและการประกอบแอป — `main.ts`, `app.ts`

**1.1 ทำไม `symptomSearch.start()` ไม่มี `await` แต่ `graphs.load()` มี?**
`graphs.load()` ต้องเสร็จก่อนรับคำขอ เพราะผังอยู่ในหน่วยความจำ ถ้ายังไม่เสร็จ route เดินผังจะหาผังไม่เจอ ส่วน `start()` โหลดโมเดล AI ซึ่งช้ามาก ถ้ารอ เซิร์ฟเวอร์จะเปิดรับคำขอไม่ได้ แม้แต่ `/health` (Render ใช้เช็กว่าเครื่องยังอยู่) จึงโหลดเบื้องหลังแล้วให้ `/symptom-search/status` บอกความคืบหน้า

**1.2 ถ้าย้าย `app.use(errorHandler)` ขึ้นไปก่อน `app.use('/health', ...)` จะเกิดอะไร?**
Express ไล่ middleware ตามลำดับที่ลงทะเบียน และ error handler จับได้เฉพาะ error ที่เกิดจากตัวที่ลงทะเบียน **ก่อนหน้ามัน** ถ้าวางไว้ก่อน routes แล้ว route โยน error จะไม่มีใครจับ ตกไปที่ตัวจัดการ error ดั้งเดิมของ Express ซึ่งตอบเป็นหน้า HTML ไม่ใช่ JSON ที่มี `code` หน้าจอจะอ่านไม่ออกและแสดง `UNKNOWN_ERROR` (ไม่ได้ลองรัน เป็นผลจากกฎของ Express)

**1.3 ถ้าจะเพิ่มบริการใหม่ที่ต้องใช้ `pool` ต้องแก้ตรงไหน?**
ใน `createApp()` ช่วง "สร้างชั้นข้อมูล → ชั้นตรรกะ" (หลัง `createDbPool()`) เพิ่ม `new XxxStore(pool)` แล้วส่งเข้า `new XxxService(...)` ถ้ามี route ใหม่ ต้องเพิ่ม `app.use('/xxx', xxxRoutes(...))` ในช่วง Express **ก่อน** `notFoundHandler`

## 2. ทางออกของ error ⭐ — `common/api-error.ts`, `common/error-handler.ts`

### 2A. ภาพรวม
**2.1 ทำไม engine ไม่โยน `ApiError` เองเลย แต่ให้ `errorHandler` มาแปลง?**
เพื่อให้ engine เป็นฟังก์ชันล้วนที่ไม่รู้จัก HTTP ถ้าฝัง status 400/409 ใน engine ตรรกะแกนกลางจะผูกกับ HTTP การแยกทำให้ทดสอบ engine ได้โดยไม่ต้องมีเว็บ และกฎ "error ไหน = รหัสไหน" อยู่ที่เดียว (ตาราง `ENGINE_ERRORS`)

**2.2 ถ้าลืมห่อ route ด้วย `asyncRoute` แล้ว `await` ใน route ล้ม ผู้ใช้จะเห็นอะไร?**
Express 4 ไม่จับ error ของฟังก์ชัน async ให้เอง คำขอนั้นไม่มีใครตอบ ผู้ใช้เห็นหน้าค้างจนหมดเวลา และ Promise ที่ล้มโดยไม่มีใครรับกลายเป็น unhandled rejection ซึ่งใน Node 15 ขึ้นไปโดยค่าเริ่มต้นอาจทำให้ทั้งเซิร์ฟเวอร์ล้ม (พฤติกรรมทั่วไปของ Node ไม่ได้ลองทำให้ล้มในโปรเจกต์นี้) ส่วน `throw` ในฟังก์ชันธรรมดา Express จับให้เอง

**2.3 ทำไม `errorHandler` ต้องอยู่หลัง routes?**
error middleware รับได้เฉพาะ error จากตัวที่ลงทะเบียนก่อนหน้า ต้องวางท้ายสุดจึงรับจากทุก route ได้ และ `notFoundHandler` (404) ก็ต้องอยู่หลัง routes เหมือนกัน ไม่งั้นจะตอบ 404 ให้ทุกคำขอก่อนถึง route จริง

### 2B. `hasHttpStatus`
**2.4 error `{statusCode: 404, message: 'x'}` ผ่านไหม? แล้ว `{statusCode: 302, message: 'x'}`?**
404 **ผ่าน** (อยู่ช่วง 400–599 มีข้อความ) 302 **ไม่ผ่าน** เพราะต่ำกว่า 400 ไม่ใช่รหัส error

**2.5 ทำไมใช้ `exception: unknown` ไม่ใช้ `Error`?**
`throw` ใน JavaScript โยนอะไรก็ได้ (ข้อความ ตัวเลข `null`) ไม่ใช่แค่ `Error` การประกาศเป็น `Error` เท่ากับโกหกตัวเอง `unknown` บังคับให้ตรวจก่อนใช้ทุกครั้ง

### 2C. `toBody`
**2.6 ถ้าสลับให้ด่านตาราง engine มาก่อน `ApiError` มีปัญหาไหม?**
ตอนนี้ไม่พังจริง เพราะ `ApiError` กับ error ของ engine เป็นคนละคลาส `instanceof` ไม่ชนกัน (ไม่ได้ลองสลับ) แต่ควรเก็บ `ApiError` ไว้ก่อนเพื่อให้กฎ "สิ่งที่โค้ดบอกชัดเจนชนะเสมอ" ไม่เปลี่ยนเมื่อวันหน้ามีคนทำคลาสสืบทอดกัน

**2.7 ทำไมด่านสุดท้ายเป็น 500 ไม่ใช่ 400?**
400 แปลว่า "ผู้ใช้ทำผิด" แต่ error ที่ไม่รู้จักมักเป็นบั๊กหรือ DB ล่ม ไม่ใช่ความผิดผู้ใช้ จึงเป็น 500 และ log stack ไว้ตามรอย

## 3. บัตรผ่าน JWT — `auth/token.ts`

**3.1 ถ้ามีคนแก้ `role` ในบัตรจาก `user` เป็น `admin` แล้วส่งมา จะเกิดอะไร?**
ลายเซ็นไม่ตรงกับข้อมูลที่แก้ `verify()` โยน error ได้ 401 ปลอมไม่ได้เพราะไม่มี `JWT_SECRET`

**3.2 ทำไม `JWT_SECRET` ไม่มีค่าเริ่มต้น (ไม่ตั้ง แอปไม่ยอมบูต)?**
ถ้ามีค่าเริ่มต้นในโค้ด ค่านั้นอยู่ใน repo ใครก็เห็น แล้วออกบัตร admin ปลอมได้ จึงให้แอปไม่บูตดีกว่ารันแบบไม่ปลอดภัย

**3.3 `fromEnv()` กับ `new TokenService(...)` ต่างกันอย่างไร ทำไมต้องมีทั้งคู่?**
`fromEnv()` อ่านและตรวจ env แล้วค่อยเรียก `new` ส่วน constructor แค่เก็บค่า แยกกันเพื่อให้ใส่ค่าตรงๆ ตอนทดสอบได้ ไม่ต้องพึ่ง env

## 4. ด่านตรวจตัวตน — `auth/auth.middleware.ts`

**4.1 ส่ง `Authorization: Bearer` (ไม่มี token ตามหลัง) ไปที่ `/auth/me` และ `/history` จะได้อะไร?**
**401 ทั้งสองที่** มี header แล้วแต่รูปแบบผิด `optionalAuth` ก็ไม่ปล่อยเป็น guest (ไม่แอบลดสิทธิ์เพื่อไม่ให้ประวัติหายเงียบๆ)

**4.2 ถ้าสลับลำดับเป็น `[requireAdmin, requireAuth]` จะเกิดอะไร?**
`requireAdmin` รันก่อนจึงยังไม่มี `request.user` ทุกคนได้ 401 รวมถึง admin จริง (`requireAdmin` ต้องวางหลัง `requireAuth` เสมอ)

**4.3 ทำไมต้องตรวจ `sub` กับ `role` ซ้ำ ทั้งที่ `verify()` ผ่านแล้ว?**
ลายเซ็นถูกแค่บอกว่าเราออกบัตรนี้จริง ไม่ได้รับประกันว่าข้อมูลข้างในถูกรูปแบบ (`verify()` คืนชนิด `unknown`) ต้องตรวจที่ขอบเขตก่อนเชื่อ

## 5. สมัคร/ล็อกอิน — `auth/auth.routes.ts`, `auth/auth.service.ts`

**5.1 ทำไมต้อง hash รหัสผ่านก่อนเก็บ ถ้าฐานข้อมูลรั่วจะต่างกันอย่างไร?**
ถ้า DB รั่ว คนร้ายได้แค่ค่า hash ไม่ใช่รหัสผ่านจริง bcrypt ช้าโดยตั้งใจและมี salt เดารหัสทีละตัวจึงแพง ถ้าเก็บรหัสจริงจะถูกยึดบัญชีทันที และคนมักใช้รหัสเดิมกับเว็บอื่นด้วย

**5.2 ถ้าตัด `dummyHash` ออก ระบบจะเสียอะไร?**
กรณีไม่พบอีเมลจะตอบเร็วกว่ากรณีพบ คนร้ายวัดเวลาแล้วเดาได้ว่าอีเมลไหนมีบัญชี (user enumeration)

**5.3 ทำไมสมัครแล้ว backend ไม่รับ `role` จาก body เลย?**
ถ้ารับ ใครก็สมัครเป็น admin เองได้ (ยกระดับสิทธิ์) admin สร้างได้ทางเดียวคือสคริปต์ `scripts/seed-admin.js`

## 6. ตรวจ input / ที่เก็บผู้ใช้ / เจ้าของ session 🔖 — `auth.dto.ts`, `users.store.ts`, `session-owner.ts`

**6.1 สมัครด้วยอีเมล `  Bob@Mail.com ` จะถูกเก็บเป็นอะไร ทำไม?**
เก็บเป็น `bob@mail.com` (`trim()` + `toLowerCase()` ใน `parseEmail`) เพื่อไม่ให้ `Bob@` กับ `bob@` กลายเป็นสองบัญชี และตอนล็อกอินค้นเจอแน่

**6.2 guest เดา `session id` ของผู้ใช้ที่ล็อกอินได้ จะดูข้อมูลได้ไหม?**
ดูไม่ได้ `ownerWhere` ของ guest คือ `(client_id = ? AND user_id IS NULL)` session ของผู้ใช้ที่ล็อกอินมี `user_id` จึงไม่ตรงเงื่อนไข ฝั่งเดินผัง `traversal.service` มี `authorize` อีกชั้น ถ้าเจ้าของเป็น user แต่ผู้ขอไม่ใช่คนเดียวกันก็ถูกปฏิเสธ (`traversal.service.ts:138-140` ไม่ได้ลองเดาจริง)

**6.3 ทำไมอีเมลซ้ำต้องแปลง 2 ชั้น (`DuplicateEmailError` แล้วค่อย `ApiError`)?**
store รู้เรื่อง DB (`ER_DUP_ENTRY`) แต่ไม่ควรรู้เรื่อง HTTP จึงแปลงเป็น error ของตัวเองก่อน แล้ว service ซึ่งเป็นผู้ตัดสินเรื่องธุรกิจค่อยบอกว่านี่คือ 409 `EMAIL_TAKEN`

## 7. rephrase 🆕 (ข้ามไว้ก่อน) — `rephrase/*`

> ตอนอ่าน ผู้พัฒนาข้ามโมดูลนี้ไว้ ยังไม่เคยเฉลย 3 ข้อนี้ เฉลยเขียนใหม่ในเอกสารนี้

**7.1 🆕 ถ้า Groq ล่มทั้งระบบ ผู้ใช้จะเห็นอะไรเปลี่ยนไปไหม ทำไม?**
ไม่เห็นความผิดปกติ `rephrase.service` จับ error แล้ว log เตือน คืน **ข้อความต้นฉบับจากคู่มือ** (`rephrased: false`) ขั้นตอนเดินต่อได้ปกติ สิ่งที่ต่างคือข้อความไม่ได้ถูกเรียบเรียงใหม่ ถ้า Groq "ตอบช้า" แทนที่จะล่มเร็ว ผู้ใช้อาจรอนานสุดตามเวลา timeout (ค่าเริ่มต้น 3 วินาที) ต่อโหนดที่ยังไม่เคยแคช เพราะผลที่ล้มไม่ถูกแคช (อ่านจากโค้ด ไม่ได้ทดสอบ)

**7.2 🆕 ทำไม guard แปลงเลขไทยเป็นอารบิกก่อนเทียบเลข?**
LLM อาจเขียนเลขเดียวกันในรูปที่ต่างกัน (`๒๒๐` กับ `220`) ถ้าเทียบตัวอักษรตรงๆ จะปฏิเสธข้อความที่ถูกต้อง หรือพลาดการเปลี่ยนค่าที่ปลอมตัวมาในรูปเลขไทย แปลงทั้งสองฝั่งเป็นอารบิกก่อน แล้วเทียบ "ค่า" ของตัวเลขจริง

**7.3 🆕 ทำไมต้องข้ามโหนด safety และโหนดจบ ทั้งที่มี guard แล้ว?**
guard ตรวจ "รูปแบบ" ไม่ตรวจ "ความหมาย" (เคยทดสอบแล้ว "ถอดปลั๊ก" → "เสียบปลั๊ก" ผ่านได้) ข้อความ safety มีความเสี่ยงสูงสุด และข้อความโหนดจบคือข้อสรุป/คำแนะนำให้ติดต่อศูนย์บริการ จึงไม่ให้ LLM แตะเลย ใช้ข้อความคู่มือตรงๆ เป็นการลดผลกระทบสูงสุดถ้า guard พลาด

## 9. history: dto 🔖 — `history/history.dto.ts`

**9.1 `?page=2&pageSize=5` ได้ค่าอะไรจาก `parseHistoryQuery`? แล้ว `?pageSize=51`?**
`{page:2, pageSize:5}` ส่วน `?pageSize=51` ได้ **400 `INVALID_HISTORY_QUERY`** เพราะเกินเพดาน 50

**9.2 ผู้ใช้ส่ง `{"helpful": "true"}` จะผ่านไหม?**

## 11. history: store 🔖 🆕 — `history/history.store.ts`

> ผู้พัฒนายังงงไฟล์นี้ จึงเฉลยข้อละเอียดขึ้น

**11.1 🆕 ทำไม `${where.sql}` ต่อข้อความใน SQL ได้ปลอดภัย แต่ห้ามต่อ `sessionId` แบบเดียวกัน?**
`where.sql` มาจากโค้ดเราเอง เป็นข้อความตายตัวสองแบบ (`(user_id = ?)` หรือ `(client_id = ? AND user_id IS NULL)`) ไม่มีค่าของผู้ใช้ปนอยู่ ค่าผู้ใช้ทั้งหมดส่งแยกทาง `?` (`params`) ส่วน `sessionId` มาจากผู้ใช้ ถ้าต่อเป็นข้อความตรงๆ ผู้ใช้ใส่ `' OR 1=1 --` เพื่อเปลี่ยน SQL ได้ (SQL injection)

**11.2 🆕 ถ้าลบ `AND expires_at > NOW()` ออกจาก `deleteCompleted` ผู้ใช้จะเห็นอะไรผิดปกติ?**
จะเกิดความไม่สอดคล้อง: session ที่หมดอายุแล้วไม่ปรากฏในรายการและเปิดดูไม่ได้ (404) แต่ถ้ารู้ id ยังสั่งลบได้สำเร็จ (204) ทำให้ตอบต่างกันระหว่างอ่านกับลบ และเผยว่า id นั้นเคยมีอยู่ ทุกคำสั่งในไฟล์ใช้เงื่อนไขชุดเดียวกันเพื่อให้ "มองเห็น" กับ "จัดการได้" เป็นชุดเดียวกัน

**11.3 🆕 `ON DUPLICATE KEY UPDATE` ทำให้ไม่ต้องเขียนอะไรเพิ่มใน service ในกรณีไหน?**
ตอนผู้ใช้ส่งคะแนนซ้ำ (แก้ความเห็น) service ไม่ต้องเขียนลำดับ "ตรวจก่อนว่ามีแถวไหม ถ้ามีค่อย UPDATE ไม่มีค่อย INSERT" ทั้งหมดอยู่ในคำสั่งเดียวที่ฐานข้อมูลทำแบบ atomic จึงไม่มีช่องให้แย่งกันระหว่างตรวจกับเขียน

## 13. admin: store ⭐ — `admin/admin.store.ts`

**13.1 ทำไม `sessionTotals` ใช้ `SUM(status = 'completed')` ถึงนับจำนวนได้ ไม่ต้อง `COUNT`?**
`status = 'completed'` เป็นนิพจน์ที่ได้ 1 (จริง) หรือ 0 (เท็จ) ต่อแถว `SUM` จึงบวก 1 ของแถวที่จริง = จำนวนแถวที่เข้าเงื่อนไข ทำให้นับหลายแบบในการสแกนครั้งเดียว

**13.3 `expired_unfinished` กับ "ยกเลิก" ต่างกันอย่างไร ทำไมนับ "ยกเลิก" ไม่ได้?**

## 17. authoring: service ⭐ — `authoring/drafts.service.ts`

**17.1 ผู้ดูแลอัปโหลด PDF สองไฟล์พร้อมกัน เกิดอะไรกับไฟล์ที่สอง ทำไมไม่เกิดร่างสองใบ?**

## 18. authoring: store — `authoring/drafts.store.ts`

**18.1 ทำไม `markReady` ต้องมี `AND status = 'drafting'` ใน SQL ทั้งที่ service รู้อยู่แล้ว?**
เป็นประตูที่ระดับ SQL ถ้าสถานะเปลี่ยนไปแล้ว (เช่นถูกเปลี่ยนเป็น `failed` ตอนเซิร์ฟเวอร์รีสตาร์ตระหว่างรอ) การอัปเดตกระทบ 0 แถวแทนการเขียนทับ ไม่ต้องพึ่งการอ่านก่อนเขียนที่มีช่องให้ race

**18.2 ถ้า `INSERT INTO nodes` พังกลางทาง (หลัง `INSERT INTO manuals` สำเร็จแล้ว) ข้อมูลใน `manuals` จะเป็นอย่างไร?**
`manuals` ถูก **rollback** ไม่เหลือในฐานข้อมูล เพราะทั้งหมดอยู่ใน transaction เดียว (`conn.rollback()`) จึงไม่มีคู่มือที่ไม่มีโหนดค้างอยู่

**18.3 `FOR UPDATE` ป้องกันอะไร ถ้าสองแอดมินกดเผยแพร่ร่างเดียวกันพร้อมกัน?**
คนแรกล็อกแถวไว้ คนที่สองต้องรอจนคนแรก commit แล้วเห็นสถานะเป็น `published` (ไม่ใช่ `ready`) จึงได้ 409 `DRAFT_NOT_READY` ไม่เผยแพร่ซ้ำสองรอบ

## 21. authoring: draft-schema 🔖 — `authoring/draft-schema.ts`

**21.2 ทำไม `graph_id` ไม่ให้ LLM กำหนดเอง?**
กัน LLM ตั้งรหัสชนกับผังเดิม ใส่อักขระแปลก หรือยาวเกิน และได้รูปแบบสม่ำเสมอ (`<manualId>_<slug>` ซ้ำต่อท้าย `_2`, `_3`)

**21.3 `parseLlmOutput` กับ `parseDraftGraphs` ต่างกันตรงไหน ทำไมไม่รวมเป็นฟังก์ชันเดียว?**
`parseLlmOutput` รับข้อความ JSON จาก LLM (ต้อง `JSON.parse`) ห่อด้วย `{graphs:[...]}` ผังมี `slug` ไม่มี `graph_id` ใช้ชื่อ `aliases` เพดาน 12 ผัง · `parseDraftGraphs` รับข้อมูลที่ parse แล้วจาก DB/PUT เป็นอาร์เรย์ตรงๆ ผังมี `graph_id` ใช้ `entry_symptom_aliases` เพดาน 60 ผัง รวมเป็นฟังก์ชันเดียวจะเต็มไปด้วย `if` แยกกรณี แยกแล้วอ่านง่ายกว่า โดยแชร์ตัวตรวจร่วมที่ `parseCommon`/`parseNodes`

## 23. ของกลาง — `common/helpers.ts`, `common/logger.ts`

**23.1 `numOrNull("0")` กับ `numOrNull(null)` ได้ค่าอะไร ต่างกันอย่างไร?**
`numOrNull("0")` → `0` (ตัวเลขศูนย์จริง) · `numOrNull(null)` → `null` (ไม่มีข้อมูล) 0 = "มีค่าและค่าคือศูนย์" null = "ไม่มีค่า" เช่นคะแนน confidence ที่ไม่เคยคำนวณ

**23.2 ทำไม `isoFromEpoch` ต้องคูณ 1000?**
`Date` ของ JavaScript ใช้มิลลิวินาที แต่ epoch จาก MySQL เป็นวินาที

**23.3 ใน `createLogger` ทำไม `error` รับ `stack` แต่ `log`/`warn` ไม่รับ?**
`error` ใช้กับความผิดพลาดที่ต้องตามรอยหาสาเหตุจึงแนบ stack ได้ ส่วน `log`/`warn` เป็นข้อความธรรมดาไม่มี stack ให้แนบ

## 27. ผังในหน่วยความจำ 🆕 — `traversal/graph.repository.ts`

> ตอนอ่านยังไม่ได้เฉลย 3 ข้อนี้

**27.1 🆕 ถ้าตอนเรียก `reload()` ฐานข้อมูลล่มกลางทาง ผู้ใช้ที่กำลังเดินผังอยู่จะได้รับผลอย่างไร?**
ไม่ได้รับผลกระทบ `loadAll` สร้างผังใหม่ใน Map ชั่วคราวก่อน ถ้าล้มกลางทางจะโยน error ก่อนถึงขั้นสลับเข้า Map จริง ผังเดิมในหน่วยความจำจึงครบเหมือนเดิม และ session ของผู้ใช้เก็บใน DB อ่านผังจาก Map เดิมต่อได้ สิ่งที่เปลี่ยนคือ admin ที่กดเผยแพร่ได้ 500 `PUBLISH_RELOAD_FAILED` (DB เขียนไปแล้วแต่ผังใหม่ยังไม่เข้าหน่วยความจำ ต้องรีสตาร์ต) (ถ้า DB ล่มจริงตอนอ่านก็ล้มตั้งแต่ก่อนเขียน อ่านจากโค้ด ไม่ได้ทดสอบ)

**27.2 🆕 ทำไมสร้าง `nextGraphs` ก่อน แล้วค่อย `clear()` + คัดลอก ไม่ `clear()` แล้วเติมตรงๆ?**
ถ้า `clear()` แล้วเติมทีละผัง และมีผังที่ข้อมูลเสียทำให้ `buildGraph` โยน error ระหว่างทาง Map จริงจะเหลือแค่ครึ่งเดียวหรือว่าง ระบบเดินผังไม่ได้ แบบสองรอบทำผลลัพธ์ให้เสร็จก่อน ช่วง `clear()` + คัดลอกไม่มี `await` คั่น คำขออื่นจึงไม่มีโอกาสเห็น Map ว่างกลางทาง

**27.3 🆕 โหนดชนิด `resolution` ที่ใน DB `outcome_kind` เป็น `NULL` จะเกิดอะไรตอนบูต?**
`buildNode` เรียก `required(row.outcome_kind, 'outcome_kind', row)` ซึ่งโยน `GraphDataIntegrityError` บอกโหนด/ผัง/คอลัมน์ที่ขาด → `loadAll()` ล้ม → `graphs.load()` ใน `createApp()` ล้ม → **เซิร์ฟเวอร์บูตไม่ขึ้น** (ตั้งใจ: "ข้อมูลเสีย = บูตไม่ขึ้น") ถ้าเกิดตอน `reload()` ผังเดิมยังอยู่ตามข้อ 27.2

## ท้ายเอกสาร: ประโยคที่ควรจำได้ (ตอบกรรมการ)
1. **LLM ร่างอย่างเดียว** คนตรวจและกดเผยแพร่เสมอ (error ข้ามไม่ได้ warning ต้องยืนยัน)
2. **error ทุกตัวไปจบที่ `errorHandler` ตัวเดียว** หน้าจอตัดสินจาก `code` ไม่ใช้ `message`
3. **ผังทั้งหมดอยู่ในหน่วยความจำ** โหลดตอนบูต ข้อมูลเสีย = บูตไม่ขึ้น · โหลดซ้ำตอนเผยแพร่ ข้อมูลเสีย = ของเดิมยังอยู่
4. **ระบบไม่เก็บไฟล์ PDF** จึงไม่รู้ว่าไฟล์เดียวกันเคยอัปโหลด กันได้เฉพาะรหัสคู่มือและรหัสผังที่ซ้ำกับของที่เผยแพร่แล้ว ซึ่งตรวจตอนอัปโหลด ตอนตรวจร่าง และตอนเผยแพร่ใน transaction
5. **ความเป็นเจ้าของบังคับที่ SQL ทุกคำสั่ง** (`ownerWhere`) ไม่ใช่แค่ใน service
6. **`null` ≠ 0 ≠ ข้อความว่าง** คะแนน/ตัวเลขที่ไม่มีข้อมูลต้องเป็น `null`
