# ตรวจว่า chunk JSON ตรงกับ PDF ต้นฉบับ (`scripts/verify_chunks_against_pdf.py`)

> 15 ต.ค. 2569 · สคริปต์ตรวจและรายงานเท่านั้น **ไม่แก้ chunk หรือ PDF** · ไม่เรียก LLM · ผลเหมือนเดิมทุกครั้งเมื่อข้อมูลเหมือนเดิม

## 1. ทำไมต้องตรวจ

chunk ใน `data/chuck/` สร้างโดยคัดลอกข้อความจาก PDF คู่มือไปให้ LLM จัดเป็นรูปแบบ `symptom / possible_cause / solution` ไม่มีโปรแกรมแปลง PDF อัตโนมัติ จึงมีความเสี่ยง 3 แบบ:

| ความเสี่ยง | ตัวอย่าง | ผลถ้าไม่ตรวจ |
|---|---|---|
| LLM แก้ตัวเลข/รหัส/ชื่อรุ่น | "30 cm" กลายเป็น "20 cm", รหัส `OC` กลายเป็น `HC` | ผู้ใช้ทำตามค่าที่ผิด |
| LLM ตัดข้อความ | ตัดขั้นตอนหรือข้อควรระวังออก | ขั้นตอนไม่ครบ |
| LLM เพิ่มเนื้อหาที่ PDF ไม่มี | แต่ง "สาเหตุ" เอง | ระบบอ้างคู่มือว่าพูดสิ่งที่คู่มือไม่ได้พูด |

โครงการนี้ถือหลักว่าทุกขั้นตอนมาจากคู่มือ สคริปต์นี้จึงเป็น **ด่านตรวจก่อนเอา chunk เข้าระบบ**

## 2. สคริปต์ทำอะไร (ตามลำดับ)

1. **ดึงข้อความจาก PDF ทีละหน้า** ด้วย `pdftotext` (ไม่ใช้โหมด `-layout` เพราะตารางสองคอลัมน์จะปนกัน)
2. **จับคู่ไฟล์ chunk กับ PDF** ด้วยตาราง `MAPPING` ที่ต้นสคริปต์ (เขียนชัดเจน ไม่เดา)
3. **normalize ทั้งสองฝั่ง:** NFKC, ตัดช่องว่าง/ขึ้นบรรทัด/อักขระล่องหน, lowercase, ตัดเลขข้อและ bullet ที่ LLM จัดใหม่
4. **หาหน้าที่เนื้อหาอยู่จริง** โดยค้นทุกหน้า แล้วคำนวณ offset ต่อไฟล์ (ใช้กับ PDF สองภาษาที่เลขหน้าที่พิมพ์ไม่ตรงกับลำดับหน้า)
5. **ให้คะแนน 2 ค่า** ต่อ chunk เทียบกับหน้าที่อ้าง
   - `cov` = สัดส่วนคำของ chunk ที่มีอยู่ในหน้านั้น
   - `order` = สัดส่วนคำที่อยู่ในหน้านั้น **ตามลำดับเดียวกัน** (คำอื่นแทรกกลางได้ คำนวณแยก symptom / cause / solution เพราะตารางใน PDF อาจสลับคอลัมน์)
6. **ตรวจ token สำคัญแยกต่างหาก:** ตัวเลข+หน่วย (เช่น `30 cm`, `60°C`), รหัสข้อผิดพลาด/รุ่น (เช่น `4C2`), ถ้าไม่อยู่ในหน้าที่อ้าง = FAIL และแยกว่า "พบในหน้าอื่น" หรือ "ไม่พบใน PDF เลย" (ร้ายแรงกว่า)
7. **คำที่ไม่อยู่ในหน้า** ค้นต่อทั้ง PDF แล้วแยกรายงานเป็น "พบในหน้าอื่น" กับ "ไม่พบใน PDF เลย"
8. **ตรวจ `safety_warning`:** เลขหน้า "(คู่มือหน้า N)" มีจริงไหม และตัวเลข/หน่วยอยู่ในหน้านั้นไหม (ไม่พบ = WARN เท่านั้น เพราะ field นี้ LLM เขียนเองเป็นภาษาไทย ไม่ใช่ข้อความที่คัดลอก)
9. **ตรวจ `chunk_id` ซ้ำ** (กระทบ unique key ใน MySQL) เป็นหมวดแยก

## 3. สถานะแต่ละแบบหมายถึงอะไร

| สถานะ | ความหมาย | ต้องทำอะไร |
|---|---|---|
| **PASS** | คำอยู่ในหน้าที่อ้างครบ (cov ≥ 0.97), ลำดับตรง (order ≥ 0.90), token สำคัญตรง, ไม่มีคำที่ PDF ไม่มี | ไม่ต้อง (แต่ **ไม่ได้พิสูจน์ว่าถูก 100%** ดูข้อ 5) |
| **WARN** | ใกล้เคียงแต่ไม่ครบ เช่น ลำดับสลับ, มีคำที่ PDF ไม่มี 1–2 คำ, ตัวเลขกับหน่วยอยู่ในหน้าแต่ไม่ติดกัน | เปิดหน้า PDF ดูด้วยตา |
| **FAIL** | สัดส่วนคำ < 0.90, token สำคัญหาย, เลขหน้าผิด, หรือมีคำที่ PDF ไม่มีตั้งแต่ 3 คำ | **ต้องแก้ chunk** หรือยืนยันด้วยตาว่าเป็นข้อยกเว้น |
| **UNVERIFIABLE** | หน้านั้นของ PDF ไม่มีข้อความ (สแกน/รูป) หรือดึงข้อความไทยไม่ได้ **ไม่นับเป็น PASS** | ตรวจด้วยตา หรือหาไฟล์ PDF ที่มี text layer |
| **UNMAPPED** | ไม่มี PDF ที่จับคู่ได้ในตาราง `MAPPING` | เติมชื่อ PDF ลงตาราง |
| **SKIPPED** | ไฟล์ที่ตั้งใจข้าม (ตอนนี้คือ Dryer ซึ่งถอดออกจากขอบเขตแล้ว) | – |
| **`PASS-TH` / `WARN-TH` / `FAIL-TH`** | ผลของ chunk ภาษาไทยในโหมด "โครงพยัญชนะ" (อ่อนกว่าภาษาอังกฤษ) ป้ายแยกและ **ไม่ทำให้ exit code เปลี่ยน** | ใช้เป็นข้อมูลประกอบ |

**เลขหน้าและ offset:** PDF ไมโครเวฟเป็นสองภาษา (ไทยตามด้วยอังกฤษ) เลขหน้าใน chunk คือเลขหน้าในส่วนอังกฤษ จึงต่างจากลำดับหน้า PDF คงที่ต่อไฟล์ (เช่น +40) ถ้าคงที่ทั้งไฟล์ = INFO ถ้า chunk ใดเบี่ยงจากค่าที่พบบ่อยสุดของไฟล์ = FAIL "เลขหน้าผิด"

## 4. วิธีรันและอ่านรายงาน

ต้องมี **`pdftotext` (poppler)** บน PATH (ไม่ต้องติดตั้งไลบรารี Python เพิ่ม) ถ้าไม่มี สคริปต์จะแจ้งและจบด้วย exit code 2

```powershell
# จากโฟลเดอร์รากของโปรเจกต์
python scripts\verify_chunks_against_pdf.py
python scripts\verify_chunks_against_pdf.py --chunks data\chuck --pdfs data\pdf --threshold 0.90
python scripts\verify_chunks_against_pdf.py --only WT10J7 --report out.md   # ตรวจไฟล์เดียว
python scripts\verify_chunks_against_pdf.py --reverse                       # ตรวจย้อนกลับ (ตัวเลือก)
```

| exit code | ความหมาย |
|---|---|
| 0 | ไม่มี FAIL และไม่มี chunk_id ซ้ำ |
| 1 | มี FAIL (ภาษาอังกฤษ/ไม่ใช่ป้าย -TH) หรือมี chunk_id ซ้ำ |
| 2 | รันไม่ได้ (ไม่มี `pdftotext` / ไม่พบโฟลเดอร์) |

**รายงาน `verification_report.md`** (UTF-8 มี BOM เปิดใน Notepad/PowerShell ได้ถูกต้อง):

| หัวข้อ | อ่านอย่างไร |
|---|---|
| 1. สรุปต่อไฟล์ | จำนวนแต่ละสถานะและ % ที่ "ตรวจไม่ได้" (UNVERIFIABLE + UNMAPPED) ของแต่ละไฟล์ |
| 2. ตาราง offset | หน้าที่พบจริง − หน้าที่ chunk อ้าง ต่อไฟล์ ถ้าไฟล์ใดมีหลายค่า = มีเลขหน้าผิด |
| 3. chunk ที่ไม่ PASS | เฉพาะ WARN/FAIL/UNVERIFIABLE พร้อม `หน้า` (ที่อ้าง) `คาด` (หน้าใน PDF ที่ตรวจ) `cov` `order` และเหตุผล |
| 4. safety_warning | จำนวน WARN และจำนวน chunk ที่ตัวเลขไม่มีใน PDF เลย |
| 5. chunk_id ซ้ำ | id, ไฟล์ที่ซ้ำ, และเนื้อหา "เหมือนกัน" (ไฟล์ซ้ำ) หรือ "ต่างกัน" (ชนกันจริง) |

ค่าเกณฑ์อยู่ที่ต้นไฟล์สคริปต์ (`WARN_THRESHOLD`, `PASS_COVERAGE`, `PASS_ORDER`, `NOWHERE_FAIL_TOKENS` และชุด `TH_*` สำหรับภาษาไทย) ตั้งจากการวัดบน chunk ภาษาอังกฤษ 539 อันในชุดข้อมูลนี้ **ไม่ใช่ค่ามาตรฐาน** ควรทบทวนเมื่อมีคู่มือใหม่

## 5. ข้อจำกัด (ต้องบอกอาจารย์ให้ครบ)

1. **PASS ไม่ได้พิสูจน์ว่าถูกต้อง 100%** การเทียบเป็นการเทียบ "คำมีอยู่ในหน้านั้น" ไม่ใช่การเข้าใจความหมาย ถ้า LLM เปลี่ยนความหมายโดยใช้คำเดิม เช่น เติมหรือตัด "ห้าม/not" สัดส่วนคำยังสูงและอาจไม่ถูกจับ
2. **ตารางและรูปใน PDF ดึงข้อความได้ไม่ครบหรือสลับลำดับ** จึงมี WARN จากการสลับคอลัมน์ และ UNVERIFIABLE กับหน้าที่เป็นภาพ (ไม่ทำ OCR)
3. **PDF ภาษาไทยดึงข้อความเพี้ยน** (วรรณยุกต์ซ้ำ ลำดับสลับ มีอักขระพิเศษ) ใช้เทียบ "โครงพยัญชนะ" ที่ไม่ตรวจวรรณยุกต์/สระ จึงเป็นป้ายแยก `-TH` และเชื่อถือน้อยกว่าภาษาอังกฤษ ในชุดนี้ WT10J7 (ไทย) ดึงตารางอาการไม่ได้ (6 จาก 7 chunk ตรวจไม่ได้)
4. **ตรวจไม่ได้ว่า "ตกหล่น"** (chunk ตัดเนื้อหาของ PDF ออก) ในทางปฏิบัติ ตัวเลือก `--reverse` เป็นเพียงสัญญาณคร่าวๆ เพราะหน้าคู่มือมีเนื้อหาอื่นอีกมาก
5. **token สำคัญใช้กฎประมาณ** (รูปแบบตัวเลข+หน่วย รหัสที่มีตัวอักษรปนตัวเลข และรหัสตัวอักษรล้วนที่อยู่หลังคำว่า code/error) อาจพลาดรหัสบางแบบ หรือจับคำทั่วไปผิดได้
6. **การตรวจตัวเลขใน `safety_warning` อ่อน** เพราะเลขตัวเดียวเช่น "5" ปรากฏในหลายหน้าของ PDF จึงเกือบไม่มีทาง "ไม่พบใน PDF เลย" ค่าที่ใช้ได้จริงคือ "ไม่อยู่หน้าที่อ้าง"
7. **ตารางจับคู่ไฟล์เป็นแบบเขียนมือ** ถ้าจับคู่ผิดไฟล์ผลจะผิดทั้งไฟล์ และมี 2 ส่วนที่ยังไม่ยืนยัน (ดูหัวข้อ 6)
8. **chunk สั้นมาก** (น้อยกว่า 8 คำที่ไม่ซ้ำ) ใช้ประมาณ offset ไม่ได้ เพราะคำทั่วไปอาจตรงหลายหน้า (ยังถูกตรวจเนื้อหาตามปกติ แค่ไม่ถูกใช้ตัดสินว่าไฟล์มี offset เท่าไร)

**ตัวอย่างสิ่งที่สคริปต์จับได้จริง:** chunk "Does not turn on" ของเครื่องซักผ้า 3 คู่มือ มีสาเหตุว่า *"…fuse **blown** or circuit breaker **tripped**"* แต่คู่มือเขียนเพียง *"Check the fuse or reset the circuit breaker"* คำ "blown" และ "tripped" ไม่มีอยู่ใน PDF ทั้งไฟล์ แสดงว่า LLM แต่งช่อง `possible_cause` เพิ่มจากขั้นตอนแก้ ซึ่งตรงกับความเสี่ยงข้อ 3 ในหัวข้อ 1

**ข้อควรระวังในการอ่านผล:** FAIL/WARN ของรุ่นเดียวกันในคู่มือที่ใช้แม่แบบเดียวกัน (WA21A, WA40F, WA5000R) จะซ้ำกัน ควรแก้ที่ต้นทางครั้งเดียว

## 7. คำถามที่อาจารย์น่าจะถาม

**ทำไมไม่ใช้ LLM ช่วยตรวจ?**
เพราะ LLM เป็นต้นเหตุของความเสี่ยงที่ต้องตรวจ การตรวจต้องเป็นการเทียบที่กำหนดได้แน่นอน อธิบายและย้อนตรวจได้ ผลไม่เปลี่ยนระหว่างรอบรัน

**PASS แปลว่าถูกต้องหรือไม่?**
ไม่ใช่ แปลว่า "คำทั้งหมดและตัวเลขสำคัญมีอยู่จริงในหน้าที่อ้าง ตามลำดับ" ซึ่งตัดความผิดพลาดประเภทแก้ตัวเลข/เติมคำออกได้ส่วนใหญ่ แต่ไม่รับประกันความหมาย (ข้อจำกัดข้อ 1)

**ทำไมบางไฟล์เป็น UNVERIFIABLE?**
PDF บางไฟล์เป็นภาพสแกนหรือดึงข้อความไม่ได้ สคริปต์ไม่ทำ OCR และไม่ยอมนับเป็น PASS เพื่อไม่ให้ตัวเลขดูดีเกินจริง

**เกณฑ์ 0.97 / 0.90 มาจากไหน?**
วัดจากการกระจายคะแนนของ chunk ภาษาอังกฤษ 539 อัน (467 อันได้ 1.00 พอดี) ตั้งให้ตัดความแตกต่างจากการสลับคอลัมน์ออก แต่ไม่ใช่ค่าที่พิสูจน์ได้ทางทฤษฎี ปรับได้ที่ต้นไฟล์

**ถ้ามีคู่มือใหม่ต้องทำอะไร?**
เพิ่มชื่อไฟล์ chunk และชื่อ PDF ในตาราง `MAPPING` แล้วรันใหม่ ถ้าไม่เพิ่ม ไฟล์นั้นจะเป็น UNMAPPED ไม่ใช่ถูกข้ามเงียบๆ
