## 1. ตรวจสถานะ deploy ก่อนวันสอบ (ทำ 30 ต.ค.)

| ตรวจ | วิธี | ผลที่ต้องการ |
|---|---|---|
| Render ใช้ branch ไหน | Render Dashboard → service `appliance-repair-backend` → Settings → Build & Deploy → **Branch** · แท็บ **Events** ดู commit ล่าสุด แล้วเทียบกับ `git log origin/main -1 --oneline` | รู้ว่า deploy commit อะไร |
| backend เป็น Express หรือ Nest | ดู Logs ตอนบูต: Express จะมี `[Database] เชื่อมต่อ MySQL สำเร็จ…`, `[GraphRepository] โหลดกราฟสำเร็จ 631 กราฟ 4739 โหนด` และ `Appliance repair backend running on port …` (`backend/src/main.ts:12-14`) ส่วน NestJS จะขึ้นต้นด้วย `[Nest]` | ตรงกับโค้ดที่จะโชว์ |
| env ครบ | Settings → Environment: `JWT_SECRET`, `DB_*`, `DB_SSL_CA`, `CORS_ORIGIN`, `SYMPTOM_SEARCH_ENABLED`, (`GROQ_API_KEY`, `GROQ_MODEL`, `AUTHORING_LLM_MODEL` ถ้าจะโชว์ LLM) | ครบ |
| backend ปกติ | เปิด `<RENDER_URL>/health` | `"status":"ok","database":"ok"` |
| ค้นหาพร้อม | `<RENDER_URL>/symptom-search/status` | `"state":"ready"`, `indexedGraphs: 631` |
| frontend ใหม่ | เปิด `https://parit-ru.github.io/appliance-repair-assistant/history` | ไม่ใช่หน้า 404 ของแอปเก่า มีเมนู "ประวัติ" และ "เข้าสู่ระบบ" |

**ถ้าเลือกแผน A (merge แล้ว deploy)** ลำดับที่ปลอดภัย
1. ทดสอบครบตามสคริปต์ข้อ 3 บนเครื่องตัวเองก่อน (ข้อ 4 แผน B)
2. commit งานที่ค้างบน `express-migration` (ผู้พัฒนาทำเอง) → push → merge เข้า `main`
3. ดู Render build/deploy จนเสร็จ → ตรวจ `/health`, `/symptom-search/status`, log บูต
4. **ห้ามรัน `npm run migrate` หรือ `seed`** กับ DB จริง (ไฟล์ 06, `docs/ops/DEPLOY.md:36`)
5. `cd frontend && npm run deploy` → ตรวจเว็บจริงทุกหน้า
6. ถ้าพัง: Render → Events → **Rollback** ไป deploy ก่อนหน้า (`docs/ops/DEPLOY.md:43`) แล้วใช้แผน B

## 4. แผนสำรอง

### แผน B — API ของ LLM ล่ม
- **กระทบน้อยมาก:** ค้นหาใช้โมเดลในเครื่อง, เดินผังไม่ใช้ LLM, rephrase ล้มหรือเกิน 3 วินาทีก็ใช้ข้อความต้นฉบับ (`backend/src/rephrase/rephrase.service.ts:47-62`)
- ที่กระทบคือการร่างผังใหม่เท่านั้น → ใช้ร่าง `ready` ที่เตรียมไว้ หรือภาพหน้าจอ
- พูด: "นี่คือเหตุผลที่ไม่ให้ LLM อยู่บนเส้นทางหลัก ระบบยังใช้งานได้ครบแม้ LLM ล่ม"

### แผน B — Render ล่ม / หลับนาน / production ยังไม่ใช่ Express → รันในเครื่อง (ไม่ต้องใช้เน็ต)
1. MySQL ในเครื่องที่ migrate + seed ไว้แล้ว (ไฟล์ 11 §5) — **เตรียมให้เสร็จก่อนวันสอบ**
2. `backend/.env` ชี้ DB ในเครื่อง, `SYMPTOM_SEARCH_ENABLED=true`, ปิด rephrase
3. `cd backend && npm run build && npm start` → รอ log "ระบบค้นหาพร้อม: 3814 ข้อความ จาก 631 ผัง"
4. `cd frontend && npm run dev` → `http://localhost:5173` (CORS ค่าเริ่มต้นของ backend อนุญาต origin นี้ `backend/src/app.ts:67`)
5. ทั้งหมดทำงานได้**โดยไม่ต้องต่ออินเทอร์เน็ต** ยกเว้นส่วน LLM เพราะโมเดล embedding อยู่ในเครื่องและห้ามโหลดจากเน็ต (`backend/src/embedding/embedding.service.ts:34`)

### แผน C — คอมพัง / เครื่องโปรเจกเตอร์มีปัญหา
- วิดีโอเดโม 5 นาที (อัด 1 พ.ย.) + ภาพหน้าจอทุกขั้นในสไลด์
- เปิดโค้ดจาก GitHub บนเครื่องอื่นได้ (`origin/express-migration`)

### ถ้าเกิด error ระหว่างเดโม
| อาการ | สาเหตุที่น่าจะเป็น | ทำอะไร |
|---|---|---|
| ขึ้น "เซิร์ฟเวอร์กำลังเริ่มทำงาน" | Render ตื่นจากหลับ | พูดเรื่อง cold start ของ free tier ระหว่างรอ |
| ค้นหาได้ "ระบบค้นหากำลังเริ่มทำงาน" (503) | โมเดลยังโหลดไม่เสร็จ | ใช้ "ดูอาการทั้งหมด" แทน แล้วอธิบายว่าเป็นการออกแบบให้เซิร์ฟเวอร์ตอบได้ระหว่างโหลด |
| CORS error | `CORS_ORIGIN` ไม่ตรง | สลับไปแผน B |
| login แล้วเด้งกลับ | token หมดอายุ/`JWT_SECRET` เปลี่ยน | ล็อกอินใหม่ |
