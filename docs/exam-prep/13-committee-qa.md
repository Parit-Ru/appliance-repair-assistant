## B. AI / Retrieval-guided design (9)

**B1 [ง่าย] embedding คืออะไร**
คือการแปลงข้อความเป็นเวกเตอร์ตัวเลข ระบบนี้ใช้ 384 มิติ ข้อความที่ความหมายใกล้กันจะได้เวกเตอร์ที่ชี้ไปทางใกล้กัน ทำให้ "ไมโครเวฟไม่ร้อน" กับ "อาหารไม่สุก" ถูกจับคู่ได้ แม้ไม่มีคำตรงกัน
📂 `backend/src/embedding/embedding.service.ts:46-55`

**B2 [ง่าย] ใช้โมเดลอะไร**
`Xenova/paraphrase-multilingual-MiniLM-L12-v2` แบบ quantized 8 บิต รันผ่าน Transformers.js/ONNX ในเครื่อง ได้เวกเตอร์ 384 มิติ ทำ mean pooling และ normalize
📂 `embedding.service.ts:5-6, 50-53`

**B3 [กลาง] ข้อความอะไรถูก embed**
ชื่ออาการภาษาไทย ชื่ออาการภาษาอังกฤษตามคู่มือ และคำพ้องที่คนน่าจะพิมพ์ ของทุกผัง รวม 3,814 รายการ ซ้ำกันแล้ว embed ครั้งเดียว เหลือ 1,936 ข้อความ ไม่ได้ embed เนื้อหาโหนดหรือข้อความคู่มือทั้งเล่ม
📂 `symptom-matcher.ts:43-62` · `symptom-search.service.ts:78-88`

**B4 [กลาง] ระบบนี้เป็น RAG ไหม**
ไม่ใช่ RAG แบบที่ให้ LLM เขียนคำตอบจากเอกสาร มีส่วน retrieval เหมือน RAG แต่สิ่งที่ retrieve คือผังขั้นตอน และให้ state machine ที่ deterministic เป็นคนพาเดิน ไม่ใช่ generator ผมเรียกว่า retrieval-guided troubleshooting state machine

**B5 [กลาง] ทำไมให้ผู้ใช้เลือกจาก 3 ผัง แทนที่จะเลือกอันดับ 1 ให้เลย**

📂 `docs/STUDY_GUIDE.md:606-617` · `SymptomSearchResults.tsx:24`

**B6 [กลาง] ถ้าผู้ใช้เลือกผิดผังจะเกิดอะไร**
คำถามแรกของหลายผังจะเป็นการยืนยันอาการ ถ้าไม่ตรง ผู้ใช้กดยกเลิกแล้วเลือกอาการอื่นได้ทุกขั้น และไม่มีขั้นไหนอันตรายโดยไม่มีคำเตือน เพราะด่านความปลอดภัยผูกกับโหนด ไม่ผูกกับการค้นหา

**B7 [ยาก] state machine ต่างจาก decision tree อย่างไร**
ผังเป็นกราฟมีทิศทาง ไม่จำเป็นต้องเป็นต้นไม้ หลายทางมาบรรจบโหนดเดียวกันได้ เช่น "อาการหายไหม" แล้วไป n_resolved และมี input node ที่เก็บตัวแปร `{{error_code}}` ไว้ใช้ภายหลัง session จึงมีสถานะคือโหนดปัจจุบัน ตัวแปร และประวัติ engine เป็น transition function `(state, action) → state ใหม่`

**B8 [ยาก] ทำไม engine เป็น pure function สำคัญอย่างไร**

📂 `backend/src/history/history.service.ts:196-221`

**B9 [ยาก] ทำไม aliases ถึงช่วย และมีข้อเสียอะไร**
alias เพิ่มจุดให้คำพูดของผู้ใช้ไปชนได้ เช่น "อาหารไม่สุก" ได้ 0.959 แต่ alias ที่เหมือนกันข้ามหลายรุ่นทำให้คะแนนเท่ากันที่ 1.000 ถ้าไม่กรองรุ่น ซึ่งเป็นเหตุผลที่ต้องเลือกรุ่นก่อน และ alias ถูกเขียนโดยผู้พัฒนา อาจมี bias ต่อคำที่ผู้พัฒนานึกออก
📂 `docs/STUDY_GUIDE.md:624-628`

## C. Retrieval / Math (9)

**C1 [ง่าย] cosine similarity คำนวณอย่างไร**
dot product หารด้วยผลคูณความยาวของสองเวกเตอร์ ได้ค่า −1 ถึง 1 ค่ายิ่งใกล้ 1 ทิศยิ่งเหมือนกัน เวกเตอร์ของเรา normalize แล้ว จึงเท่ากับ dot product แต่โค้ดคำนวณสูตรเต็มไว้
📂 `symptom-matcher.ts:20-41`

**C2 [กลาง] คำนวณให้ดูด้วยมือหน่อย**
q = (1,2,2), d = (2,1,2) จะได้ dot = 2+2+4 = 8 และความยาวทั้งคู่เท่ากับ 3 → cos = 8/9 ≈ 0.889 ผ่านเกณฑ์ 0.55 · d = (2,−1,0) ได้ dot = 0 → cos = 0 ตัดทิ้ง
📂 `docs/exam-prep/03-retrieval-and-similarity.md` §3

**C3 [กลาง] threshold 0.55 กับ Top 3 อยู่ตรงไหน**
`MATCH_THRESHOLD = 0.55`, `MAX_RESULTS = 3` กรองด้วย `score >= 0.55` แล้วตัดเหลือ 3 อันแรก คะแนนต่อผังคือคะแนนสูงสุดของป้ายในผังนั้น
📂 `symptom-search.service.ts:11-12` · `symptom-matcher.ts:64-96`

**C4 [ยาก] 0.55 มาจากไหน** ⚠
มาจากชุดตั้งเกณฑ์ 56 ข้อในโปรเจกต์เวอร์ชันก่อน ซึ่ง AI ช่วยร่างและเป็นของคู่มือแอร์ ยังไม่ได้ปรับกับข้อมูล 4 ประเภทปัจจุบัน ผมจึงไม่อ้างว่าเป็นค่าที่ดีที่สุด มีแผนวัด top-1/top-3 และอัตราปฏิเสธนอกขอบเขต แล้วเลือกค่าใหม่ด้วย Youden's J บนชุด tuning แยกจากชุด report
📂 `troubleshoot-assistantv2/data/eval/review_sheet_tuning.md` · `docs/exam-prep/10-evaluation.md`

**C5 [กลาง] metadata filter ทำอย่างไร**
กรองล่วงหน้าด้วย `manualId` ก่อนคำนวณ cosine เหลือเฉพาะข้อความของผังในคู่มือรุ่นนั้น และตอนเริ่ม session ตรวจซ้ำว่าผังเป็นของรุ่นที่ส่งมา ไม่งั้นตอบ 400
📂 `symptom-search.service.ts:165-168` · `traversal.service.ts:62-64`

**C6 [กลาง] ความซับซ้อนเท่าไร**
O(N·d) ต่อคำค้น โดย N คือจำนวนข้อความหลังกรอง และ d = 384 ถ้าไม่กรองคือประมาณ 3,814 × 384 ≈ 1.46 ล้านครั้ง ซึ่งเร็วมากสำหรับ CPU บวก embed คำค้นอีกครั้ง
📂 ไฟล์ 03 §7

**C7 [กลาง] ใช้ RAM เท่าไร**
เวกเตอร์ 1,936 × 384 × 4 ไบต์ ≈ 3 MB ส่วนที่หนักคือโมเดลและ runtime ทั้ง process วัดได้ราว 270–310 MB จากเพดาน 512 MB ของ Render free ตามที่วัดในโปรเจกต์เวอร์ชันก่อน และดูสดได้ที่ `/symptom-search/status`
📂 `symptom-search.service.ts:200-211`

**C8 [ยาก] ถ้าคะแนนเท่ากันเรียงอย่างไร**
เรียงตาม graphId ตามตัวอักษร เพื่อให้ผลคงที่ทุกครั้ง แต่ก็เป็นข้อเสีย ถ้าไม่กรองรุ่น อาจเห็นแค่ผังที่ชื่อขึ้นก่อน ซึ่งเป็นอีกเหตุผลที่บังคับเลือกรุ่น
📂 `symptom-matcher.ts:82-87`

**C9 [ยาก] ถ้าข้อมูลโตเป็นล้านข้อความจะทำอย่างไร**
เปลี่ยนเป็น ANN เช่น HNSW หรือ vector DB, cache เวกเตอร์ใน DB แทนการ embed ตอนบูต และแยก embedding service ออกไป สำหรับข้อมูลระดับปัจจุบัน brute force ให้ผลแม่นยำ 100% และง่ายกว่า
📂 ไฟล์ 03 §9

## D. LLM / Prompt / Hallucination (9)

**D1 [ง่าย] LLM ทำอะไรในระบบ**
สองอย่าง คือ เรียบเรียงข้อความของขั้นที่ไม่อันตรายให้อ่านง่าย ซึ่งปิดได้และปิดเป็นค่าเริ่มต้น กับช่วย admin ร่างผังจาก PDF ที่ต้องผ่าน validator และคนตรวจ LLM ไม่ได้เป็นผู้สร้างคำแนะนำที่ผู้ใช้เห็นตอนเดินผัง

**D2 [กลาง] ใช้ LLM ตัวไหน temperature เท่าไร**

📂 `groq-llm.client.ts:27` · `draft-llm.client.ts:95` · `backend/.env.example`
⚠ ถ้าถูกถามชื่อรุ่นที่ deploy ให้ตอบตามค่าที่ตั้งใน Render dashboard (ไม่อยู่ในโค้ด)

**D3 [กลาง] prompt ของ rephrase บังคับอะไร**
ห้ามเพิ่ม ลบ หรือเปลี่ยนความหมาย ห้ามเปลี่ยนตัวเลข รหัส ชื่อรุ่น ห้ามเพิ่มคำแนะนำหรือบอกขั้นถัดไป และให้ถือว่าข้อความที่ได้รับเป็นสิ่งที่ต้องเรียบเรียง ไม่ใช่คำถามที่ต้องตอบ
📂 `groq-llm.client.ts:5-11`

**D4 [ยาก] ถ้า LLM ไม่ทำตาม prompt ล่ะ**
ไม่เชื่อ prompt อย่างเดียว ผลต้องผ่าน guard ที่เป็นโค้ด คือ ชุดตัวเลขต้องเหมือนเดิม (แปลงเลขไทยก่อน), คำภาษาอังกฤษ/รหัสต้องครบและไม่มีคำเกิน, จำนวนคำว่า "ไม่" ต้องเท่าเดิม, ความยาว 0.5–1.6 เท่า, ไม่มีลิงก์หรือ markdown ไม่ผ่านข้อใดข้อหนึ่งก็ใช้ข้อความต้นฉบับ
📂 `rephrase-guard.ts:26-61`

**D5 [ยาก] guard นี้กันได้ทุกกรณีไหม** ⚠
ไม่ได้ทุกกรณี มันตรวจรูปผิว ไม่ได้เข้าใจความหมาย ถ้า LLM เปลี่ยนคำกริยาแต่ตัวเลขและคำปฏิเสธเท่าเดิมก็อาจผ่าน ระบบจึงไม่ rephrase โหนดอันตรายและโหนดสรุปเลย ปิดเป็นค่าเริ่มต้น และหน้าจอมีปุ่มดูข้อความต้นฉบับ

## L. "ทำไมไม่ใช้ X" (12)

**L1 [กลาง] ทำไมไม่ใช้ ChatGPT ตรงๆ**
ตรวจไม่ได้ว่าจะตอบอะไร อาจแต่งขั้นตอนหรือละคำเตือน ไม่มีหน้าคู่มืออ้างอิงที่เชื่อถือได้ มีค่าใช้จ่ายต่อคำถาม และส่งข้อความผู้ใช้ออกไปภายนอก ระบบนี้เตรียมคำแนะนำล่วงหน้าและตรวจได้ก่อนเผยแพร่

**L2 [ยาก] ทำไมไม่ทำ RAG ที่ให้ LLM สรุปคำตอบจาก chunk**
RAG ลด hallucination ได้แต่ไม่หมด LLM ยังสรุปผิดหรือเชื่อม chunk ผิดได้ และคำเตือนบังคับด้วย prompt ได้แค่ขอร้อง งานซ่อมเครื่องใช้ไฟฟ้ามีความเสี่ยงด้านความปลอดภัย จึงเลือกให้ขั้นตอนเป็นข้อมูลที่ตรวจแล้ว และให้ engine บังคับด่าน แลกกับความยืดหยุ่นที่น้อยลง

**L3 [กลาง] ทำไมไม่ fine-tune โมเดล**
ไม่มีชุดข้อมูลคำถาม-คำตอบมากพอ, fine-tune ไม่ได้รับประกันว่าจะไม่แต่ง, ต้องเทรนใหม่ทุกครั้งที่เพิ่มคู่มือ และตรวจย้อนกลับไม่ได้ว่าความรู้มาจากหน้าไหน การเก็บความรู้เป็นผังแก้ได้ทันทีและอ้างอิงได้

**L4 [กลาง] ทำไมไม่ใช้ LangChain**
ระบบใช้ LLM แค่ 2 จุด แต่ละจุดเป็น HTTP call เดียว เขียนเองไม่กี่สิบบรรทัด อ่านและอธิบายได้ทุกบรรทัด ควบคุม timeout/guard ได้เอง LangChain จะเพิ่ม abstraction และ dependency ที่ไม่ได้ใช้
📂 `groq-llm.client.ts:20-44`

**L5 [กลาง] ทำไม MySQL ไม่ใช่ PostgreSQL**
ข้อมูลเป็นตารางสัมพันธ์ธรรมดา ไม่ต้องใช้ฟีเจอร์เฉพาะของ PostgreSQL เพราะไม่ได้ใช้ pgvector ผู้พัฒนาคุ้นกับ MySQL และใช้ Aiven ฟรีที่มีอยู่แล้ว ถ้าวันหน้าอยากเก็บเวกเตอร์ใน DB จริง PostgreSQL + pgvector เป็นตัวเลือกที่ดี

**L6 [กลาง] ทำไมไม่ใช้ vector DB / pgvector**
ข้อความแค่ ~2,000 ข้อความ brute force เร็วพอและแม่นยำ exact การเพิ่ม DB อีกตัวเพิ่มทั้งค่าใช้จ่ายและความซับซ้อน เวกเตอร์ทั้งหมดใช้ RAM แค่ ~3 MB

**L7 [กลาง] ทำไมใช้ embedding รันในเครื่อง แทน API เช่น OpenAI embeddings**
หนึ่ง ไม่มีค่าใช้จ่ายต่อคำค้น สอง ข้อความผู้ใช้ไม่ออกนอก server สาม ไม่พึ่งเน็ตหรือ rate limit ของผู้ให้บริการ ระบบค้นหาจึงทำงานได้แม้ API ภายนอกล่ม สี่ ผลคงที่เพราะรู้แน่ว่าใช้โมเดลไฟล์ไหน และโมเดลรองรับหลายภาษาในขนาดที่รันบน Render free ได้
📂 `embedding.service.ts:34-40`

**L8 [ยาก] แล้วข้อเสียของ embedding ในเครื่องคืออะไร**
โมเดลเล็ก คุณภาพอาจต่ำกว่าโมเดลใหญ่ผ่าน API, ใช้ RAM ราว 250–300 MB และทำให้บูตช้าลงประมาณ 1 นาที ถ้าคุณภาพไม่พอจะลองโมเดลอื่นได้ เพราะทั้งระบบผูกกับโมเดลแค่ที่ `EMBEDDING_MODEL_ID`
📂 `embedding.service.ts:5`

**L9 [กลาง] ทำไมย้ายจาก NestJS มา Express**
เหตุผลจริงคือตอนไล่อ่านโค้ดเตรียมสอบ ส่วนที่อธิบายไม่ได้คือกลไกของ Nest เช่น decorator, DI, guard กับ ExecutionContext ไม่ใช่ตรรกะของระบบ Express เป็นฟังก์ชันธรรมดาที่อ่านจากบนลงล่างได้ ผมย้ายทีละโมดูล 8 เฟส ตรรกะไม่เปลี่ยน และเทียบผล HTTP 120 กรณีตรงทั้งหมด ไม่ได้ย้ายเพราะเรื่องประสิทธิภาพ
📂 `docs/STUDY_GUIDE.md` §5.7

**L10 [ยาก] ย้าย framework ช่วงใกล้สอบไม่เสี่ยงเหรอ** ⚠
เสี่ยงครับ จึงทำทีละโมดูลและเทียบกับ baseline ทุกเฟส แต่ยอมรับว่าบางส่วนยังไม่ได้ทดสอบมือหลังย้าย เช่น อัปโหลด PDF จริงและ rephrase กับ Groq จริง และ production ยังเป็นเวอร์ชันเดิม [อัปเดตตามสถานะวันสอบ]

**L11 [กลาง] ทำไมไม่ใช้ ORM เช่น Prisma/TypeORM**
อยากเห็นและอธิบาย SQL ทุกคำสั่ง รวมถึงควบคุม transaction และ query สถิติเอง ข้อมูลไม่ซับซ้อนจนต้องใช้ ORM ข้อแลกคือต้องแปลงชนิดข้อมูลเอง เช่น DECIMAL ที่ mysql2 คืนเป็น string

ผู้ใช้พิมพ์ภาษาพูด แต่ผังเขียนตามคู่มือและมีสองภาษา keyword จะพลาดเมื่อใช้คำพ้อง embedding เทียบความหมายได้ข้ามภาษา แต่ยอมรับว่ายังไม่ได้วัดเทียบกับ keyword ด้วยข้อมูลจริง hybrid search เป็นงานต่อยอดที่ดี
