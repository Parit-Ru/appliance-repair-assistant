# LLM เรียบเรียงถ้อยคำ + fallback (ทางเลือก — ปิดเป็นค่าเริ่มต้น)

**สถานะ (13 ต.ค. 2569):** เขียนครบ เชื่อมเข้ากับระบบแล้วในรูป **patch 0003 (backend) + 0004 (frontend)** ตรวจกับโค้ดปัจจุบันในแซนด์บ็อกซ์: backend 219 เทสผ่าน · frontend 61 เทสผ่าน · smoke test HTTP 15/15 กับ LLM จำลอง · **ยังไม่เคยเรียก Groq จริง** (ไม่มี API key) และยังไม่ได้นำ patch เข้า repo

> คำที่คุณนึกไม่ออก คือ **fallback** (ทางสำรอง) หรือเรียกเป็นหลักการว่า **graceful degradation** (ระบบเสื่อมลงอย่างนุ่มนวล: ส่วนเสริมใช้ไม่ได้ ก็ถอยกลับไปใช้ของเดิมที่ใช้ได้แน่ ไม่ล้มทั้งระบบ) ในที่นี้ "ของเดิม" คือข้อความต้นฉบับจากคู่มือ

## 1. หลักการ (ตาม TOR §3 ข้อ 3)

| LLM ทำได้ | LLM ทำไม่ได้ |
|---|---|
| เปลี่ยนสำนวนของข้อความ 1 โหนดให้อ่านง่ายขึ้น | เลือกขั้นตอนถัดไป · เปลี่ยนตัวเลือกคำตอบ · เพิ่ม/ตัดขั้นตอน · เปลี่ยนตัวเลข รหัส ชื่อเฉพาะ · แตะโหนดความปลอดภัย/สิ้นสุด |

การเรียก LLM เกิด **หลังจาก** engine ตัดสินสถานะและบันทึกลงฐานข้อมูลเสร็จแล้ว รับ/คืนข้อความเดียว (ไม่เห็น session ผัง ตัวเลือกถัดไป หรือสิ่งที่ผู้ใช้พิมพ์) จึงไม่มีช่องทางให้ LLM มีอิทธิพลต่อลำดับขั้นตอน

```
POST /sessions/:id/actions
   │  1. engine.submitAction()  ← ตัดสินขั้นถัดไป (ไม่มี LLM)
   │  2. sessionStore.update()  ← บันทึกสถานะ
   │  3. toResponse()
   │       └─ RephraseService.rephrase(node.text)   ← ขั้นเดียวที่ใช้ LLM
   │              ปิดอยู่/โหนดเสี่ยง/ล้ม/ช้า/ไม่ผ่านด่าน ──► displayText = null  (fallback)
   ▼
response: { node: { text: "ต้นฉบับจากคู่มือ" … }, displayText: "ข้อความที่ปรับถ้อยคำ" | null }
```

## 2. Fallback: ทุกกรณีที่ผิดปกติผู้ใช้ยังเห็นข้อความจากคู่มือ

| สถานการณ์ | ผู้ใช้เห็น | ระบบทำ |
|---|---|---|
| `REPHRASE_ENABLED` ไม่ใช่ `true` / ไม่มี `GROQ_API_KEY` / ไม่มี `GROQ_MODEL` | ข้อความต้นฉบับ | ไม่เรียก LLM (ถ้าเปิดแต่ตั้งค่าไม่ครบ มี warn ตอนบูต) |
| โหนด `safety_critical` หรือโหนดสิ้นสุด (resolution/escalation) | ข้อความต้นฉบับ **เสมอ** | ไม่ส่งข้อความนั้นให้ LLM เลย (ตรวจใน smoke test) |
| LLM ตอบ error (HTTP 4xx/5xx, เครือข่ายล่ม) | ข้อความต้นฉบับ | `displayText = null`, log warn |
| LLM ช้าเกิน `REPHRASE_TIMEOUT_MS` (ค่าเริ่มต้น 3000) | ข้อความต้นฉบับ | ยกเลิกคำขอ (`AbortController`) |
| LLM ล้ม/ช้าติดกัน 3 ครั้ง | ข้อความต้นฉบับ **ทันที ไม่ต้องรอ timeout** | **วงจรตัด (circuit breaker)** หยุดเรียก 60 วินาทีแล้วลองใหม่ |
| ข้อความที่ได้ไม่ผ่านด่านตรวจ (ตัวเลข/ชื่อเฉพาะ/คำปฏิเสธ/ลิงก์/ความยาว) | ข้อความต้นฉบับ | `displayText = null`, log warn พร้อมเหตุผล |
| ข้อความที่เคยเรียบเรียงสำเร็จแล้ว | ข้อความที่ปรับถ้อยคำ (จากแคช) | ใช้ต่อได้แม้ LLM ล่ม |
| โค้ดฝั่งเรียบเรียงโยน error แปลกๆ | ข้อความต้นฉบับ | `try/catch` ใน `displayTextOf` คืน `null` |

ฝั่งหน้าจอมีรั้วซ้ำ: `pickDisplayNode` ไม่แทนข้อความของโหนดความปลอดภัย/สิ้นสุดแม้เซิร์ฟเวอร์ส่งมา และไม่แสดงป้ายถ้าข้อความเท่าต้นฉบับ

**ที่วัดได้จริง (smoke test, LLM จำลองในเครื่อง, timeout 500 ms):** LLM ตอบ 500 → เดินจนจบและลำดับ nodeId เหมือนตอน LLM ปกติทุกตัว · LLM ช้า 2.5 วินาที → 5 ขั้นใช้ ~1.7 วินาที (ถ้ารอเต็มจะ ~12.5 วินาที) · LLM ล่มทั้งตัว → ทำงานปกติ

## 4. เปิดใช้อย่างไร (หลังนำ patch เข้า repo)

| ตัวแปร | ที่ตั้ง | หมายเหตุ |
|---|---|---|
| `REPHRASE_ENABLED=true` | Render → Environment | ต้อง `true` เป๊ะๆ ค่าอื่น = ปิด |
| `GROQ_API_KEY` | Render (ความลับ) | ห้าม commit |
| `GROQ_MODEL` | Render | ชื่อโมเดลที่ Groq มีอยู่ — ไม่มีค่าเริ่มต้น (ชื่อเปลี่ยนได้) |
| `REPHRASE_TIMEOUT_MS` | ไม่บังคับ (3000) | ผมแนะนำ 1500–2000 บน Render free เพื่อไม่ให้ผู้ใช้รอนานต่อขั้น |
| `GROQ_ENDPOINT` | ไม่บังคับ | ใช้กับผู้ให้บริการอื่นที่เข้ากับ OpenAI หรือเซิร์ฟเวอร์จำลองตอนทดสอบ |

ถ้าตั้งไม่ครบ ระบบทำงานเหมือนเดิมทุกประการ (fallback) — ปิดฟีเจอร์ได้ทันทีโดยเอา `REPHRASE_ENABLED` ออก ไม่ต้อง deploy โค้ดใหม่

## 5. สิ่งที่ยังไม่ได้พิสูจน์ / ข้อจำกัด

- **ยังไม่เคยเรียก Groq จริง:** `GroqLlmClient` เขียนจากรูปแบบ API ที่เข้ากับ OpenAI (`/openai/v1/chat/completions`) ทดสอบกับเซิร์ฟเวอร์จำลองที่ผมเขียนเองเท่านั้น ก่อนใช้จริงต้องลองด้วยคีย์จริงและตรวจ URL/ชื่อโมเดล
- **ด่านตรวจจับได้เฉพาะสิ่งที่ตรวจด้วยกฎ** (ตัวเลข ชื่อ คำปฏิเสธ รูปแบบ) พิสูจน์ความหมายเท่าเดิมไม่ได้ ตัวอย่างที่หลุดได้: สลับเงื่อนไขโดยไม่เปลี่ยนจำนวน "ไม่" หรือเปลี่ยนลำดับสองขั้นตอนในประโยคเดียว → จึงห้ามใช้กับโหนดความปลอดภัย และควรสุ่มอ่านผลจริงก่อนเปิด
- **ยังไม่มีการวัดว่าอ่านง่ายขึ้นจริง** — ถ้าไม่ดีขึ้น ไม่ควรเปิด (ความเสี่ยงเพิ่มโดยไม่มีประโยชน์)
- ความหน่วง: ทุกขั้นที่ข้อความยังไม่อยู่ในแคชจะรอ LLM สูงสุด `REPHRASE_TIMEOUT_MS` (ผู้ใช้คนแรกของแต่ละข้อความเจอก่อน คนถัดไปใช้แคช) แคชอยู่ในหน่วยความจำ หายเมื่อ Render รีสตาร์ท
- ความเป็นส่วนตัว: ส่งไปยังผู้ให้บริการภายนอกเฉพาะ **ข้อความของโหนดจากคู่มือ** ไม่ส่งสิ่งที่ผู้ใช้พิมพ์หรือรหัสเซสชัน
- ผลลัพธ์อาจไม่คงที่ระหว่างการสาธิต (แม้ `temperature: 0` ผู้ให้บริการไม่รับประกัน) — แคชช่วยให้ข้อความเดิมเหมือนเดิมตลอดช่วงที่แอปยังไม่รีสตาร์ท

## 6. วิธีวัดก่อนเปิดจริง (ครึ่งวัน)

1. ตั้งคีย์ในเครื่อง (ไม่ commit) เดินผังทั้ง 13 ผังผ่านเว็บในเครื่อง ดู log warn ว่าอัตราที่ถูกปฏิเสธเท่าไร และเหตุผลอะไร
2. สุ่มอ่าน 20 โหนดที่ผ่านด่าน เทียบกับต้นฉบับ: ความหมายเท่าเดิมไหม อ่านง่ายขึ้นไหม (บันทึกเป็นตาราง)
3. ถ้าพบความหมายเปลี่ยนแม้ข้อเดียว หรืออัตราผ่านต่ำ → ไม่เปิดใช้ และรายงานเป็น "ผลการทดลอง" (เป็นผลที่มีค่าเช่นกัน)
