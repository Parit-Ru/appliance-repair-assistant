# คู่มือแปลงคู่มือซ่อมเป็นเครื่องสถานะ (สำหรับ 4 ประเภทเป้าหมายของ TOR)

ใช้เมื่อต้องเพิ่มข้อมูลไมโครเวฟ / ตู้เย็น / ทีวี / เครื่องซักผ้า จากคู่มือ Samsung SelfRepair ตามที่ TOR ฟังก์ชันที่ 1–2 กำหนด

> **หลักที่ห้ามละเมิด:** เนื้อหาทุกโหนดต้องมาจากคู่มือหน้าที่ระบุ ผู้ช่วย AI (รวมถึงผม) **ไม่ควรเติมขั้นตอนซ่อมจากความรู้ทั่วไป** เพราะ TOR วางหลักว่าระบบต้องอ้างอิงคู่มือได้ทุกขั้นตอน และขั้นตอนเกี่ยวกับไฟฟ้า/ความร้อน/แรงดันสูง (ไมโครเวฟมีตัวเก็บประจุแรงดันสูง ตู้เย็นมีสารทำความเย็น) ผิดแล้วเป็นอันตรายต่อผู้ใช้ ถ้าใช้ AI ช่วยสกัดข้อความจาก PDF ผู้พัฒนาต้องไล่เทียบทุกโหนดกับหน้าคู่มือด้วยตัวเอง

## ภาพรวมขั้นตอน

| ขั้น | ทำอะไร | ผลที่ได้ | ตรวจด้วย |
|---|---|---|---|
| 1 | เลือกรุ่นและคู่มือ 1 เล่มต่อ 1 ไฟล์ข้อมูล | `manual_id` เช่น `samsung_ms23_xxx` | — |
| 2 | ไล่หัวข้อ "แก้ปัญหา/Troubleshooting" ของคู่มือ แล้วทำตารางอาการ → หน้า | ตารางอาการ (ดูแบบฟอร์มข้างล่าง) | ผู้พัฒนาอ่านเอง |
| 3 | วาดผังทีละอาการบนกระดาษ: คำถามใช่/ไม่ใช่ → การกระทำ → จบ | ผังกระดาษ | อ่านเทียบหน้าคู่มือ |
| 4 | พิมพ์เป็น JSON ตามแม่แบบ `draft/data/templates/manual.template.json` | `data/manuals/<manual_id>.json` | `validate-graphs.js` |
| 5 | เติม `data/equipment/equipment.json` ของประเภทนั้น พร้อมที่มา | รายการอุปกรณ์ | `validate-graphs.js --equipment` |
| 6 | ให้บุคคลที่สองตรวจเทียบคู่มือ (หรืออย่างน้อยตรวจซ้ำเองหลังพัก 1 วัน) | บันทึกการตรวจ | รายการตรวจด้านล่าง |
| 7 | `npm run seed` (นำเข้า MySQL) แล้วทดสอบเดินผังบนเว็บ | ข้อมูลในระบบ | smoke test + เดินด้วยมือ |

## ชนิดโหนด (ตรง `types.ts`) เลือกอย่างไร

| ชนิด | ใช้เมื่อ | ฟิลด์ที่ต้องมี | เส้นออก |
|---|---|---|---|
| `checkpoint` | ถามผู้ใช้ตอบ ใช่/ไม่ใช่ **ทีละเรื่อง** | `question`, `on_yes`, `on_no` | 2 เส้น |
| `instruction` | บอกให้ผู้ใช้ลงมือทำ 1 อย่าง | `content`, `next` | 1 เส้น |
| `input` | ต้องการค่าจากผู้ใช้ เช่น รหัสข้อผิดพลาด | `prompt`, `input_type`, `store_as`, `next`, (`pattern`, `on_invalid`) | 1–2 เส้น |
| `resolution` | จบ: ปัญหาหาย หรือเป็นการทำงานปกติ | `content`, `outcome_kind` = `user_fixed` / `normal_behavior` | ไม่มี |
| `escalation` | จบ: แก้เองไม่ได้ ส่งต่อศูนย์บริการ | `content`, `outcome_kind` = `handoff_informed` (คู่มือบอกให้ติดต่อ) / `handoff_unknown` (ไม่รู้สาเหตุ) | ไม่มี |

## กฎการเขียนที่ตัวตรวจบังคับหรือเตือน

1. **ทุกผังต้องมีทางไปจบ** และควรมี `escalation` อย่างน้อยหนึ่งโหนด (TOR ข้อ 4: ไม่คาดเดา) — ตัวตรวจ: ไม่มีทางจบ = error, ไม่มี escalation = เตือน
2. **ห้ามมีวงที่ออกไม่ได้** และห้ามมีโหนดที่ไม่มีใครชี้ถึง
3. **ขั้นตอนที่เกี่ยวกับไฟฟ้า/ความร้อน/แรงดัน/การเปิดฝา/แก๊ส** ต้องเป็น `instruction` ที่ `"safety_critical": true` และมี `"safety_warning"` (ข้อความเตือนที่ผู้ใช้ต้องติ๊กยืนยัน) — ระบบจะบล็อกที่เซิร์ฟเวอร์จนกว่าจะยืนยัน ตัวตรวจ: `safety_critical` อยู่ได้เฉพาะ `instruction`, ต้องมี `safety_warning`, และเตือนเมื่อ instruction มีคำที่บ่งอันตราย (เบรกเกอร์ ปลั๊ก แรงดัน ถอดฝา ฯลฯ) แต่ไม่ได้ตั้ง
4. **ห้ามเขียนขั้นตอนที่คู่มือไม่ได้บอก** ถ้าต้องการเพิ่มคำอธิบายของผู้พัฒนา ใส่ใน `author_note` (แยกจากข้อความคู่มือ — หน้าจอและรายการอุปกรณ์ใช้แยกแหล่งที่มาได้)
5. **`page_range` และ `source` ต้องถูกต้อง** เพราะหน้าจอแสดง "ที่มาของขั้นตอนนี้: คู่มือ … หน้า N" ทุกขั้น (TOR ฟังก์ชัน 6)
6. **หนึ่งคำถาม หนึ่งเรื่อง** — ถ้าคู่มือเขียน "ตรวจ A และ B" แยกเป็นสอง checkpoint เพื่อให้ตอบ ใช่/ไม่ใช่ ได้ตรง
7. **`entry_symptom_th` + `entry_symptom_aliases`** ใช้ทั้งแสดงผลและค้นหา: เขียนชื่ออาการเป็นภาษาไทยที่ผู้ใช้พูดจริง และเพิ่มสำนวนพูด 2–4 คำ (สั้น ไม่ซ้ำกันระหว่างผัง) — คำพ้องที่คล้ายกันมากระหว่างสองผังทำให้ผังสองอันได้คะแนนใกล้กัน (ดูผลประเมิน: `water_drips_outdoor` vs `condensation_indoor`)
8. **`graph_id`** ตัวพิมพ์เล็ก/ตัวเลข/ขีดล่างเท่านั้น และขึ้นต้นด้วย `manual_id_`
9. **ห้ามเหลือ `TODO`** — ตัวตรวจจะไม่ยอมให้ผ่านแม่แบบที่ยังไม่แก้

## รายการตรวจก่อนนำเข้า (ขั้น 6)

- [ ] ทุกโหนดเทียบกับหน้าคู่มือที่ระบุแล้ว (ข้อความ, ตัวเลข, หน่วย, ชื่อปุ่ม/ฟังก์ชัน)
- [ ] ไม่มีขั้นตอนที่ผู้พัฒนาเพิ่มเองโดยไม่อยู่ใน `author_note`
- [ ] ทุกขั้นตอนไฟฟ้า/ความร้อน/แรงดัน/เปิดฝา เป็น `safety_critical` พร้อมข้อความเตือนที่คู่มือใช้
- [ ] ผังที่มีขั้นตอนอันตราย: ถามตัวเองว่า "ถ้าผู้ใช้ทำตามโดยไม่อ่านคำเตือน จะเกิดอะไร" และคำเตือนปรากฏก่อนขั้นตอนนั้นจริง
- [ ] `node backend/scripts/validate-graphs.js --strict --equipment` ผ่านโดยไม่มีคำเตือนที่ยังไม่ได้พิจารณา
- [ ] เดินผังบนเว็บครบทุกเส้นทางอย่างน้อย 1 ครั้ง (ตอบ ใช่ ทั้งหมด / ไม่ ทั้งหมด) — `path-coverage.spec.ts` เดินให้อัตโนมัติ แต่ **อ่านเฉพาะ `samsung_ac_ar70h.json`** (ระบุ path ตายตัว) ต้องแก้สเปคให้วนไฟล์ใน `data/manuals/` เมื่อเพิ่มคู่มือใหม่
- [ ] เพิ่มคำค้นสำหรับผังใหม่ลงชุดประเมิน (ดู `EVALUATION-PLAN.md`)

## คำสั่งที่เกี่ยวข้อง

```
node backend/scripts/validate-graphs.js path/to/new_manual.json      # ตรวจไฟล์เดียว
node backend/scripts/validate-graphs.js --strict --equipment          # ตรวจทุกไฟล์ใน data/manuals + equipment
node backend/scripts/validate-graphs.js --self-test                   # ตรวจว่าตัวตรวจเองยังจับข้อผิดพลาดได้
cd backend && npm run seed && npm run seed:equipment                  # นำเข้า MySQL (⚠️ ฐานข้อมูลใช้ร่วมกับ FixStep)
```
